## 一、产品定位

### 1.1 SSMSBoostPlus 产品矩阵中的定位

SSMSBoostPlus 是面向 SQL Server 开发人员和 DBA 的内部效率工具集，作为 SSMS（SQL Server Management Studio）的扩展插件运行。版本历史（LocalHistory）是 SSMSBoostPlus 中 **"代码管控"子产品线**的核心模块，与版本守卫（VersionGuard）构成"检测-记录-回溯"的完整闭环。

```
SSMSBoostPlus 产品矩阵
├── 代码管控（Code Governance）
│   ├── 版本历史（LocalHistory）     ← 本模块
│   └── 版本守卫（VersionGuard）      ← 联动模块
├── [其他功能模块]
└── ...
```

### 1.2 版本历史 vs 版本守卫的关系

| 维度 | 版本历史（LocalHistory） | 版本守卫（VersionGuard） |
|------|--------------------------|--------------------------|
| 触发方式 | 用户主动查询 | 被动检测外部变更 |
| 数据来源 | MESBASE 数据库 DDL Trigger 记录 | SSMS 文件系统监控 |
| 核心价值 | "过去发生了什么" — 追溯与回退 | "现在正在发生什么" — 实时防护 |
| 用户心智 | 事后审计工具 | 事前/事中防护工具 |
| 联动关系 | 为版本守卫提供历史比对基准 | 触发版本历史自动弹出 |

**关键洞察**：版本历史是"数据层"，版本守卫是"感知层"。当前两个模块的联动（AutoOpenOnExternalChange）配置已定义但无消费代码，这是 **短期最高优先级**的集成任务。

### 1.3 产品价值主张

**一句话定位**：让 SQL Server 数据库对象的每一次变更都可追溯、可对比、可回退。

**核心价值**：
- **安全感**：DDL Trigger 自动记录，零配置即可获得完整的变更审计链
- **效率**：在 SSMS 内直接浏览、比对、回退，无需切换工具
- **协作透明**：谁在什么时间从哪台机器改了什么，一目了然

## 二、目标用户与场景

| 期望 | 直观的差异对比，支持逐行逐词高亮 |

|------|------|

### 2.2 核心用户场景（User Journey）

#### 场景 A：紧急故障排查

```
1. 生产存储过程突然报错
2. DBA 打开 SSMS，定位到该存储过程
3. 打开版本历史窗口 → 看到最近 3 次变更记录
4. 点击最近一次变更 → 查看差异对比
5. 确认是某开发人员误改了 WHERE 条件
6. 一键生成回滚脚本 → 在编辑器中预览 → 执行回滚
7. 故障恢复，总耗时 < 5 分钟
```

#### 场景 B：日常开发版本回溯

```
1. 开发人员修改了 5 版存储过程，发现第 3 版的逻辑最优
2. 打开版本历史窗口 → 筛选该对象的所有历史版本
3. 对比第 3 版与当前版本差异
4. 复制第 3 版关键代码片段 → 合并到当前版本
5. 继续开发
```

#### 场景 C：合规审计

```
1. 审计人员要求提供某数据库过去 30 天的所有 DDL 变更记录
2. DBA 打开版本历史 → 选择数据库 → 导出变更记录列表
3. 筛选特定用户/特定时间段的变更
4. 导出为报告提交审计
```

## 三、功能优先级评估

### 3.1 优先级排序方法

采用 **RICE 模型**（Reach × Impact × Confidence ÷ Effort）结合 **MoSCoW 法则**：

- **Reach**：受影响用户数（1-10）
- **Impact**：对用户的价值影响（1-10）
- **Confidence**：对评估的确信度（20%-100%）
- **Effort**：实现工作量（人天）

## 四、用户体验设计

### 4.1 信息架构

```
版本历史 ToolWindow
├── 工具栏
│   ├── 数据库选择器（ComboBox，支持搜索过滤）
│   ├── 对象搜索框（TextBox，支持模糊匹配）
│   ├── 刷新按钮
│   ├── 钉住按钮（Pin/Unpin）
│   └── 设置按钮（齿轮图标）
├── 主数据区
│   ├── 对象摘要列表（左侧面板）
│   │   ├── ObjectName（对象名称）
│   │   ├── ObjectType（类型：PROCEDURE/FUNCTION/VIEW/TABLE/TRIGGER）
│   │   └── VersionCount（版本数量徽标）
│   └── 版本记录列表（右侧 DataGrid）
│       ├── PostTime（变更时间）
│       ├── EventType（CREATE/ALTER/DROP）
│       ├── LoginName（操作人）
│       ├── HostName（来源机器）
│       └── 操作按钮（对比/回滚/在编辑器中打开）
├── 状态栏
│   ├── 记录总数
│   ├── 最后刷新时间
│   └── 数据库连接状态
└── 差异对比弹窗（Dialog）
    ├── 左面板：历史版本（或版本A）
    ├── 右面板：当前版本（或版本B）
    ├── 差异导航条（差异块快速跳转）
    └── 工具栏：同步滚动开关、在编辑器中打开、复制
```

### 4.2 核心操作流程

#### 流程 1：浏览变更记录

```
打开 ToolWindow
  → 自动推导当前连接数据库
  → 自动推断当前焦点对象
  → 加载该对象的版本历史
  → 用户可切换数据库/搜索其他对象
  → 点击版本记录行查看详情
```

#### 流程 2：差异比对

```
选中版本记录 → 点击"对比"
  → 弹出 DiffDialog
  → 左栏显示选中历史版本
  → 右栏显示当前版本（或选中的另一个历史版本）
  → 差异行高亮 + 子词级高亮
  → 同步滚动浏览
  → 关闭弹窗 → 返回 ToolWindow（焦点正确归还）
```

#### 流程 3：版本回退

```
选中目标版本 → 点击"回滚"
  → 系统判断 RestoreType：
      ALTER 版本 → 直接生成 ALTER 脚本
      CREATE 版本 → 转换为 ALTER 脚本
      DROP 版本 → 查找上一条非 DROP 版本生成 CREATE 脚本
  → 在编辑器中打开回滚脚本
  → 用户审查后手动执行
```

### 4.3 交互设计原则

1. **零等待感知**：大脚本加载时显示进度指示器，避免界面假死
2. **渐进式披露**：默认显示关键字段，详情按需展开
3. **容错设计**：MESBASE 不可用时给出明确提示和操作指引，而非静默失败
4. **焦点管理**：弹窗关闭后焦点正确归还，不劫持用户操作流
5. **状态保持**：钉住模式下窗口不随 DTE 焦点切换而刷新内容

### 5.4 SWOT 分析

#### SSMSBoostPlus 版本历史

| 优势（Strengths） | 劣势（Weaknesses） |
|-------------------|-------------------|
| DDL Trigger 实时追踪，零延迟 | 无 Git 集成，无法与代码仓库联动 |
| 子词级差异高亮，精度领先 | 无静态数据对比能力 |
| 智能回滚脚本生成（ALTER/CREATE/DROP） | 缺少差异导航、忽略空白等高级对比功能 |
| SSMS 原生 ToolWindow 集成，体验流畅 | 无依赖检查，回滚可能引入新问题 |
| 内部工具，无许可费用 | 缺少团队协作功能 |

| 机会（Opportunities） | 威胁（Threats） |
|----------------------|----------------|
| 版本守卫联动可形成独特闭环体验 | Redgate 在 SSMS 生态中品牌认知度极高 |
| 开源后可吸引社区贡献 | 微软 SSDT + Git 方案在 .NET 团队中普及 |
| 审查日志可满足合规审计需求 | 竞品持续迭代，功能差距可能扩大 |
| 轻量级定位可吸引中小团队 | 用户可能倾向于"够用就行"的免费方案 |

### 5.5 差异化策略建议

1. **"实时"作为核心差异化**：DDL Trigger 实时追踪 vs 竞品的定时快照，这是结构性优势
2. **版本守卫联动闭环**：检测→记录→回溯的完整链路，竞品无此能力
3. **轻量化定位**：不做 Git 集成（那是另一条产品线），聚焦"SSMS 内的变更安全网"
4. **子词级精度**：继续保持 DiffPlex SubPieces 的精度优势
5. **免费 + 开源**：对 Redgate/ApexSQL 的定价形成降维打击

## 六、产品路线图

成为 SQL Server 生态中 **最轻量、最实时、最易用**的数据库对象变更管控工具。

## 七、成功指标（KPI）

### 7.1 北极星指标

**"每周通过版本历史成功回溯或回滚的数据库对象变更次数"**

衡量版本历史功能为用户创造的实际价值——每一次成功的回溯/回滚都意味着避免了一次潜在的生产事故或开发返工。

### 7.2 核心 KPI

#### 使用活跃度

| 指标 | 定义 | 目标值（V1.0 发布后 3 个月） |
|------|------|------------------------------|
| 周活跃用户数（WAU） | 每周至少使用 1 次版本历史的用户数 | ≥ 团队 DBA/开发人员的 60% |
| 日均查询次数 | 每天版本历史窗口被打开的次数的中位数 | ≥ 20 次/天 |
| 功能发现率 | 知道版本历史功能存在的目标用户占比 | ≥ 80% |

#### 功能有效性

| 指标 | 定义 | 目标值 |
|------|------|--------|
| 回滚成功率 | 生成的回滚脚本成功执行的比率 | ≥ 95% |
| 差异比对准确率 | 差异高亮与实际变更一致的比例 | ≥ 99% |
| 数据加载时间（P95） | 95% 的查询在 N 秒内返回结果 | ≤ 3 秒（1000 条记录内） |

#### 用户满意度

| 指标 | 定义 | 目标值 |
|------|------|--------|
| NPS（净推荐值） | 用户推荐意愿评分 | ≥ 30 |
| 关键任务完成率 | 用户能在 3 分钟内完成"查找变更→对比→回滚"全流程 | ≥ 85% |
| 缺陷密度 | 每千行代码的已知缺陷数 | ≤ 2.5 |

#### 业务价值

| 指标 | 定义 | 目标值 |
|------|------|--------|
| 平均故障恢复时间（MTTR） | 从发现问题到回滚成功的平均时间 | 相比无工具时缩短 50% |
| 变更审计覆盖率 | 有版本历史记录的数据库对象占比 | ≥ 95%（MESBASE 已部署的实例） |

## 八、产品风险标注与建议

### 8.1 风险矩阵

| 风险 | 等级 | 描述 | 建议 |
|------|------|------|------|
| 用户接受度风险 | 🟡 中 | 用户可能习惯用 Git 或其他工具管理数据库变更 | 强调"零配置"和"实时性"优势，降低使用门槛 |
| 市场时机风险 | 🟢 低 | 内部工具，无外部市场压力 | 按节奏推进即可 |
| 竞品威胁风险 | 🟢 低 | 内部工具不直接竞争，开源后才有竞品关系 | 开源前做好差异化定位 |
| 技术可行性风险 | 🟡 中 | 大脚本虚拟化渲染在 WPF 中实现有技术挑战 | 提前做技术预研，准备降级方案 |
| 运营推广风险 | 🔴 高 | 内部工具容易被忽略，用户不知道有版本历史功能 | 在 SSMSBoostPlus 启动页/菜单中加入功能引导 |

### 8.2 产品优化建议

1. **尽快实现版本守卫联动**：这是版本历史从"好用"到"不可或缺"的关键跃迁
2. **优先修复焦点劫持问题**：这是最影响用户体验的缺陷，每次使用都会触发负面感受
3. **MESBASE 不可用提示必须有操作指引**：不仅仅是"不可用"，还要告诉用户"怎么让它可用"
4. **考虑在 V1.5 加入差异导航条**：这是与竞品差距最大的交互功能
5. **建立用户反馈渠道**：在 ToolWindow 状态栏加入"反馈"入口，收集真实使用场景
