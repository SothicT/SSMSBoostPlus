# SSE 零缓冲流式渲染 — 开发技能卡

## 适用场景

当需要在 WPF/WinForms 桌面应用中实现 **AI 大模型接口的实时流式响应显示**时，使用本技能卡。

触发词：流式渲染、SSE 实时显示、大模型逐 token 输出、AI 弹窗实时、Markdown 渲染、AI 接口响应慢。

---

## 一、架构全景

### 整体架构图

```
C# / WPF 层
  AIStreamResultDialog
    RequestWebView  (WebView2 + marked.js 渲染 Markdown)
    ResponseWebView (NavigateToString + JS 引擎)
         |
         | WebMessageReceived
         | <--- {type:"complete"} / {type:"error"} / {type:"status"}
         |
WebView2 (Chromium) 层
  marked.min.js        -- 业界标准 Markdown 解析库（v12.0.2，35KB）
  stream-engine.js
    callChatApi()      -- 两步 API 调用
      Step 1: GET /chat/api/open → chat_id
      Step 2: POST /chat/api/chat_message/{chatId} → SSE 流
    processSseLine()  -- SSE 帧解析（W3C 规范）
    processSseEvent() -- JSON 解析，提取 content + reasoning_content
    doRender()        -> md(fullText) -> marked.parse() -> innerHTML

  fetch --POST--> http://ai-api/chat/api/chat_message/{chatId}
        <--SSE-- data: {"content":"token"} / data: {"reasoning_content":"..."}
```

### 核心设计决策

| 决策 | 选择 | 原因 |
|------|------|------|
| 渲染引擎 | WebView2 (Chromium) | 支持 ES6+/fetch/ReadableStream |
| Markdown 解析 | marked.js v12.0.2（嵌入资源） | 业界标准，处理所有边界情况 |
| SSE 客户端 | 内联 fetch + ReadableStream | 嵌入 HTML 无法用 npm |
| C#-JS 通信 | postMessage / WebMessageReceived | WebView2 标准通道 |
| HTML 加载 | NavigateToString | 无需文件系统依赖 |
| CORS 处理 | --disable-web-security | NavigateToString 的 origin 为 null |
| 请求区渲染 | WebView2 + marked | 与响应区共用 CSS 和渲染引擎 |

## 二、AI 大模型接口响应时间长的问题与解决思路

### 2.1 问题现象

用户点击 AI 菜单后，弹窗长时间空白，体验差。典型时序：

```
t=0s    用户点击菜单
t=0.1s  弹窗出现，状态："正在连接 AI 服务..."
t=2~5s  API 返回第一个 SSE 事件（思考阶段，content 为空）
t=5~15s 思考结束，开始输出正式回答
t=15~30s 回答完成
```

### 2.2 根因分析

| 层面 | 原因 | 影响 |
|------|------|------|
| **AI 模型层** | 大模型推理本身耗时（Qwen3 思考链可能 10s+） | 无法在客户端解决 |
| **API 架构层** | 两步调用：先 GET /open 拿 chat_id，再 POST 发消息 | 多一次 RTT |
| **渲染层** | 手写 Markdown 解析器 Bug 导致部分内容不渲染 | 看似"卡住"实为渲染失败 |
| **用户体验层** | 弹窗在 API 响应前完全空白 | 用户无感知进度 |

### 2.3 解决思路与实施

#### 思路一：两步 API 降低连接等待（已实施）

**方案**：将原来的单步 SSE 请求拆为两步：

```
Step 1: GET /chat/api/open → 立即返回 chat_id（<200ms）
Step 2: POST /chat/api/chat_message/{chatId} → SSE 流式响应
```

**收益**：Step 1 快速返回后，前端立即更新状态为"AI 正在思考..."，用户感知到系统在工作。

**代码位置**：`stream-engine.js` → `callChatApi()`

```javascript
// Step 1: 快速获取 chat_id
const openResponse = await fetch(BASE_URL + '/chat/api/open', { ... });
const chatId = openData.data;
updateStatus('AI 正在思考...', true);  // ← 立即反馈

// Step 2: 发起 SSE 流
const chatResponse = await fetch(BASE_URL + '/chat/api/chat_message/' + chatId, { ... });
```

#### 思路二：思考过程实时渲染（已实施）

**方案**：API 返回的 SSE 事件包含 `reasoning_content`（AI 思考过程）字段，在思考阶段实时渲染到折叠区域，让用户看到 AI "在想什么"。

**收益**：思考阶段（通常 5~15s）不再是空白等待，用户能实时看到推理过程。

**代码位置**：`stream-engine.js` → `processSseEvent()`

```javascript
function processSseEvent(data) {
    const parsed = JSON.parse(data);
    // 思考内容 → 实时渲染到折叠区
    const reasoning = parsed.reasoning_content;
    if (reasoning) {
        thinkText += reasoning;
        scheduleThinkRender();
    }
    // 正式回答 → 渲染到主内容区
    const content = parsed.content;
    if (content) {
        fullText += content;
        scheduleRender();
    }
}
```

#### 思路三：非模态弹窗（已实施）

**方案**：使用 `Show()` 而非 `ShowDialog()`，弹窗不阻塞 SSMS 编辑器。

**收益**：用户可以在等待 AI 响应时继续操作 SSMS，甚至同时发起多个 AI 请求。

**代码位置**：各 `AI*Command.cs`

```csharp
_activeDialog = new AIStreamResultDialog(title, promptText, baseUrl, authToken, promptText);
_activeDialog.Closed += (_, _) => _activeDialog = null;
_activeDialog.Show();  // ← 非模态，不阻塞
```

#### 思路四：requestAnimationFrame 零延迟渲染（已实施）

**方案**：每个 SSE 事件到达后立即调度渲染，使用 `requestAnimationFrame` 保证每帧最多渲染一次。

**演进历程**：

| 版本 | 调度策略 | 问题 |
|------|---------|------|
| v12 | setTimeout(fn, 30) 防抖 | 连续数据时 timer 被 reset，等暂停才渲染 |
| v13 | requestAnimationFrame + 8 字符阈值 | 更好但仍不够即时 |
| v14+ | requestAnimationFrame 零阈值 | 每个 SSE 事件立即渲染，无延迟 |

**核心原则**：setTimeout 防抖不适合流式场景。requestAnimationFrame 保证每帧最多渲染一次且不跳帧。

#### 思路五：用 marked 库替换手写 Markdown 解析器（已实施）

**方案**：手写 Markdown 解析器在流式场景下有大量边界 Bug，彻底替换为业界标准的 `marked` 库（v12.0.2，35KB 精简版）。

**收益**：彻底解决 Markdown 渲染导致的"内容消失"问题（本质是渲染失败，不是接口慢）。

**详细见下方第五节。**

### 2.4 优化效果

| 优化项 | 优化前 | 优化后 |
|--------|--------|--------|
| 首次反馈时间 | 5~15s（空白等待） | <0.5s（状态立即更新） |
| 思考阶段体验 | 空白 | 实时显示思考过程 |
| 渲染可靠性 | 手写解析器频繁 Bug | marked 库稳定渲染 |
| 用户操作自由度 | 模态弹窗阻塞 SSMS | 非模态，可继续操作 |

## 三、数据流详解

### 3.1 完整请求-响应流程

1. 用户右键选中 SQL，点击 AI 菜单项
2. C# AICommand 获取代码、构建 Prompt
3. 创建 AIStreamResultDialog，调用 Show()（非模态）
4. OnLoaded 中初始化 WebView2 环境（含 --disable-web-security）
5. 初始化 RequestWebView：用 marked 渲染请求内容 Markdown
6. 初始化 ResponseWebView：NavigateToString 加载 HTML + marked.min.js + stream-engine.js
7. JS 自动执行 callChatApi()
8. Step 1: GET /chat/api/open → 获取 chat_id
9. 状态更新："AI 正在思考..."（通过 postMessage 通知 C#）
10. Step 2: POST /chat/api/chat_message/{chatId} → SSE 流式响应
11. 每个 SSE 事件经 processSseLine → processSseEvent 解析
12. reasoning_content → thinkText → 实时渲染到折叠思考区
13. content → fullText → requestAnimationFrame(doRender)
14. doRender: md(fullText) → marked.parse() → innerHTML
15. 流结束: finishStream() 通过 postMessage 通知 C#
16. C# OnJsStreamComplete 停止计时器、更新状态

### 3.2 SSE 帧解析逻辑

SSE 协议格式（W3C spec）：

- 空行 = 事件分隔符，触发 dispatchEvent
- data: 多行 = 用 \n 连接
- 冒号后空格 = 可选
- 冒号开头 = 注释行，忽略

解析状态机：

```
读取一行文本
  |
  +-- 空行 -> 派发当前事件，重置状态
  +-- 冒号开头 -> 忽略(注释)
  +-- field: value
        +-- data -> 累积到 sseData
```

### 3.3 SSE 事件 JSON 结构

```json
{
  "content": "SELECT",           // 正式回答内容（逐 token）
  "reasoning_content": "分析...",// AI 思考过程（逐 token）
  "is_end": false                // 是否结束
}
```

## 五、Markdown 渲染：从手写到 marked 库

### 5.1 为什么放弃手写解析器

手写 Markdown 解析器在流式渲染场景下有大量无法修复的 Bug：

| Bug | 根因 | 表现 |
|-----|------|------|
| 代码块 if/else 互斥 | `hasUnclosedFence=true` 时跳过已关闭代码块处理 | 完整代码块不渲染，后续 Markdown 全部失败 |
| 行内代码正则吃掉三反引号 | `` `/`([^`]+)`/g `` 在 `` ``` `` 之前执行 | 围栏标记被吃掉，代码块不渲染 |
| `<pre><code>` 被 split 拆分 | 代码内容有换行符，split('\n') 后被包裹 `<p>` | 代码块 HTML 结构被破坏 |
| `\x00` 占位符不稳定 | null 字符在 JS 中行为不可预测 | 占位符恢复失败 |
| HTML 转义时机冲突 | 代码内容被双重 escHtml 转义 | `&lt;` 显示为 `&amp;lt;` |
| `<li>` 未包裹 `<ul>/<ol>` | 列表项直接推入数组 | 列表样式不正确 |

### 5.2 marked 库集成方案

**marked.min.js** 作为嵌入资源（35KB），在 HTML 中先于 stream-engine.js 加载：

```csharp
// csproj 声明
<EmbeddedResource Include="Resources\marked.min.js" />

// HTML 注入顺序
<script>{markedLib}</script>          <!-- 1. 先加载 marked 库 -->
<script>{streamEngineJs}</script>     <!-- 2. 再加载业务引擎 -->
```

### 5.3 流式渲染特殊处理

流式输出时，代码块围栏可能是奇数个（未闭合），marked 会把后续所有文本当代码块。解决方案：检测到奇数个 `` ``` `` 时，自动补一个闭合标记。

```javascript
function md(text) {
    if (!text) return '';
    if (typeof marked === 'undefined') {
        return escHtml(text).replace(/\n/g, '<br>');
    }
    try {
        marked.setOptions({ gfm: true, breaks: true, silent: true });
        var renderText = text;
        var fenceCount = (renderText.match(/```/g) || []).length;
        if (fenceCount % 2 !== 0) {
            renderText = renderText + '\n```';  // 补全闭合标记
        }
        return marked.parse(renderText);
    } catch (e) {
        return escHtml(text).replace(/\n/g, '<br>');  // 降级
    }
}
```

### 5.4 请求区 Markdown 渲染

请求区也使用 WebView2 + marked 渲染，与响应区共享同一套 CSS：

```csharp
private string BuildRequestHtml()
{
    var requestJson = JsonConvert.SerializeObject(_requestContent);
    return $@"<!DOCTYPE html>
<html><head><meta charset=""utf-8"">
<style>{SharedCss}</style>
<script>{CachedMarkedLib.Value}</script>
</head><body>
<div id=""content""></div>
<script>
(function() {{
    var text = {requestJson};
    marked.setOptions({{ gfm: true, breaks: true, silent: true }});
    var renderText = text;
    var fenceCount = (renderText.match(/```/g) || []).length;
    if (fenceCount % 2 !== 0) renderText += '\n```';
    document.getElementById('content').innerHTML = marked.parse(renderText);
}})();
</script>
</body></html>";
}
```

## 六、踩坑记录与解决方案

### 6.1 CORS 陷阱

| 现象 | 根因 | 解决 |
|------|------|------|
| Failed to fetch | NavigateToString 的页面 origin 为 null，Chromium 拦截跨域 fetch | --disable-web-security |

**IE11 无此问题**：WebBrowser 的 NavigateToString 属于"本地计算机区域"，自动绕过 CORS。Chromium 严格执行 W3C CORS 规范。

### 6.2 渲染延迟（分批显示而非逐 token）

| 版本 | 调度策略 | 问题 |
|------|---------|------|
| v12 | setTimeout(fn, 30) 防抖 | 连续数据时 timer 被 reset，等暂停才渲染 |
| v13 | requestAnimationFrame + 8 字符阈值 | 更好但仍不够即时 |
| v14+ | requestAnimationFrame 零阈值 | 每个 SSE 事件立即渲染 |

**核心原则**：setTimeout 防抖不适合流式场景。requestAnimationFrame 保证每帧最多渲染一次且不跳帧。

### 6.3 WebView2 DLL 不在 bin 输出目录

WebView2 NuGet 包使用 build/targets 特殊打包，DLL 需从 NuGet 缓存复制：

```
%USERPROFILE%\.nuget\packages\microsoft.web.webview2\1.0.2903.40\
  lib\net462\Microsoft.Web.WebView2.Core.dll
  lib\net462\Microsoft.Web.WebView2.Wpf.dll
  runtimes\win-x64\native\WebView2Loader.dll
```

### 6.4 SSE 空行语义冲突

SSE 协议空行 = 事件分隔符，但 Markdown 也需要空行做段落分隔。处理策略：

- SSE 层：空行触发 processSseEvent 派发
- JS 业务层：data 解析后的 content 自然包含 `\n`，marked 会正确处理段落

### 6.5 Qwen3 思考标签变体

Qwen3 模型输出 reasoning_content 字段而非 `<think>` 标签，需要在 processSseEvent 中分别提取：

```javascript
function processSseEvent(data) {
    const parsed = JSON.parse(data);
    if (parsed.reasoning_content) { thinkText += parsed.reasoning_content; }
    if (parsed.content) { fullText += parsed.content; }
    if (parsed.is_end === true) { isComplete = true; }
}
```

### 6.6 DLL 被 SSMS 锁定无法覆盖

部署时如果 SSMS 正在运行，DLL 文件被锁定无法覆盖：

```powershell
# 必须先关闭 SSMS
Get-Process -Name 'Ssms' -ErrorAction SilentlyContinue | Stop-Process -Force
Start-Sleep -Seconds 2
Copy-Item $src $dst -Force
```

### 6.7 marked 库嵌入资源未更新

`CachedMarkedLib` 使用 `Lazy<string>`，首次访问后缓存。如果修改了 `marked.min.js` 但未重新编译，旧的嵌入资源会被使用。确保每次修改后执行 `dotnet build`。

## 七、复用指南

### 7.1 在其他 WPF 项目中复用

最小依赖：
1. NuGet: Microsoft.Web.WebView2 (>=1.0.2903.40)
2. NuGet: Microsoft.Xaml.Behaviors.Wpf
3. 复制 `stream-engine.js` 和 `marked.min.js` 作为嵌入资源

集成步骤：

1. XAML 中声明两个 WebView2 控件（请求区 + 响应区）
2. C# 初始化时创建 WebView2 环境（含 --disable-web-security）
3. 注册 WebMessageReceived 事件
4. 构建 HTML 字符串，注入 BASE_URL/AUTH_TOKEN/PROMPT_MESSAGE
5. 先注入 `marked.min.js`，再注入 `stream-engine.js`
6. NavigateToString 加载
7. JS 自动发起两步 API 调用并实时渲染

### 7.2 切换到其他 AI API

只需修改 C# 端的 baseUrl/authToken 和 JS 端的 API 路径：

| API 类型 | endpoint | 认证方式 |
|----------|----------|----------|
| 内置两步 API | GET /chat/api/open + POST /chat/api/chat_message/{id} | Bearer Token |
| OpenAI 兼容 | POST /v1/chat/completions | Bearer API Key |

### 7.3 添加新的 AI 功能

复制任一 AI*Command.cs 的模式：

1. 获取选中的 SQL 代码
2. 构建功能特定的 Prompt（含 `@SSMSBOOST` 前缀和 `@SSMSBOOST_SQL_性能分析SKILLS`）
3. 确定 baseUrl 和 authToken
4. 创建 AIStreamResultDialog 并 Show()（非模态）
5. 检查 dialog.IsStreamCompleted / dialog.HasError
6. 处理结果（如替换编辑器内容）
