# 01 - 智能代码补全（IntelliSense）

## 一、功能概述

SQL Prompt 的智能代码补全是其最核心的功能，提供远超 SSMS 原生 IntelliSense 的上下文感知代码补全体验。

### 核心差异（vs SSMS 原生）

| 对比维度 | SSMS 原生 | SQL Prompt |
|----------|----------|------------|
| 候选列表 | 列出所有对象（含数据库名、用户、系统对象等），按字母排序 | 根据上下文判断意图，智能过滤，优先推荐最可能的目标 |
| 示例场景 | `SELECT * FROM` 后列出数据库名等不相关对象 | 识别需要表名，直接列出表名候选 |
| 响应速度 | 较大数据库可能延迟 | 缓存到内存，响应更快 |

## 二、功能细节

### 2.1 补全类型清单

| 补全类型 | 触发场景 | 支持程度 |
|----------|---------|---------|
| **表名补全** | `SELECT * FROM` 后 | 完整支持 |
| **列名补全** | 已指定表名后自动提示该表列名 | 完整支持 |
| **通配符展开** | 选中 `*` 按 Tab → 展开为完整列名列表 | 完整支持 |
| **函数补全** | 输入函数名 → 含参数信息提示 | 完整支持 |
| **存储过程补全** | 输入名称后按 Enter → 列出参数 | 完整支持 |
| **JOIN 补全** | ON 条件建议 | 支持 |
| **关键字补全** | 自动调整大小写 + 上下文相关建议 | 完整支持 |
| **INSERT 扩展** | `INSERT INTO 表名` 后按 Enter → 列出字段 | 完整支持 |
| **ALTER 扩展** | ALTER 相关语句补全 | 完整支持 |
| **CTE 补全** | CTE 内上下文感知 | 支持 |
| **SQLCMD 模式** | SQLCMD 上下文敏感建议 | 支持 |
| **链接服务器对象** | 链接服务器上的表/列名称建议 | 支持 |
| **Synonyms** | 同义词引用的数据库对象 | 支持（可配置） |

### 2.2 缺失功能（vs dbForge SQL Complete）

以下功能 SQL Prompt 目前不支持：

- **EXEC 语句扩展**：执行存储过程时无参数提示
- **UPDATE 语句扩展**：UPDATE 语句无字段提示
- **GROUP BY 非聚合列**：不自动列出非聚合列
- **JOIN 子句自动生成**：不自动生成完整 JOIN 语句
- **行数统计信息**：候选列表中不显示表的行数
- **列选择器**：无可视化列选择界面

### 2.3 触发机制

| 触发方式 | 操作 |
|----------|------|
| 自动触发 | 键入代码时自动弹出候选列表 |
| Idea 图标 | 点击 SQL Prompt 的提示图标触发列名展开等 |
| Tab 键 | 选中 `*` 按 Tab → 展开为列名 |
| Enter 键 | INSERT/存储过程名后按 Enter → 展开参数 |
| 模式切换 | `Ctrl+Alt+Space` 在补全/建议模式间切换 |

## 三、技术原理推测

### 3.1 上下文感知引擎

SQL Prompt 的核心是**基于语法位置的意图判断**：

```
┌──────────────────────────────────────────┐
│              SQL 解析流程                  │
├──────────────────────────────────────────┤
│ 输入 SQL 文本                             │
│   ↓                                      │
│ 实时解析 → 确定光标所在语法位置              │
│   ↓                                      │
│ 位置分类：                                │
│   - FROM 后 → 候选类型 = 表名              │
│   - SELECT 后(有别名) → 候选类型 = 列名    │
│   - WHERE 后 → 候选类型 = 列名(过滤条件)    │
│   - 函数参数内 → 候选类型 = 参数提示         │
│   ↓                                      │
│ 从缓存中查询对应类型对象                    │
│   ↓                                      │
│ 应用排序算法                               │
│   ↓                                      │
│ 展示候选列表                               │
└──────────────────────────────────────────┘
```

### 3.2 候选排序算法

| 排序层级 | 策略 | 说明 |
|----------|------|------|
| 第1优先级 | 最近使用 | 用户最近查询过的表排在最前面 |
| 第2优先级 | 上下文匹配 | 按对象类型匹配权重 |
| 第3优先级 | 字母排序 | 无历史记录时按字母排列 |

**借鉴思路**：通过在持久化存储中记录用户的使用历史（表名+时间戳），形成一个简单的 LRU 权重系统。每次查询对象时排序使用：
```
score = (isRecent ? 100 : 0) + (isTypeMatch ? 50 : 0) + (alphabeticalScore)
```

### 3.3 实时解析技术

关键技术挑战是**增量解析**——用户每键入一个字符都需要重新解析 SQL 语句，但不能每次都从头解析整个文档。推测实现方式：

1. **基于上次解析结果增量更新**：只重新解析修改位置的附近范围
2. **使用 LL(k) 解析器**：对 T-SQL 语法的支持需要足够的 lookahead
3. **容错解析**：代码处于编辑状态时语法通常不完整，需要容错处理

## 四、用户体验亮点

1. **无缝集成**：补全与 SSMS 编辑器深度整合，无额外窗口或模态对话框
2. **智能过滤**：不相关的系统对象被自动过滤，减少干扰
3. **渐进式提示**：先选表 → 再选列，分步引导用户
4. **非侵入式**：候选列表可随时按 Escape 关闭，不打断用户思路

## 五、可实现的借鉴方案

### 5.1 技术路线

| 步骤 | 内容 | 技术选型 |
|------|------|---------|
| 1 | 实现 T-SQL 语法解析器 | 基于 ANTLR 的 T-SQL 语法文件，或自建轻量解析器 |
| 2 | 实现 Schema 缓存层 | 从 `INFORMATION_SCHEMA` / `sys.objects` 拉取元数据 |
| 3 | 实现上下文判断引擎 | 基于 AST 的节点类型判断光标位置 |
| 4 | 实现候选排序 | LRU 历史权重 + 类型匹配权重 |
| 5 | 集成 SSMS 编辑器 | 通过 Visual Studio Shell 的 `ITextBuffer` / `ICompletionBroker` |

### 5.2 关键技术挑战

| 挑战 | 说明 | 应对策略 |
|------|------|---------|
| **实时性能** | 每键入一个字符都要解析+查询+渲染 | 增量解析 + 缓存中间结果 + 300ms 防抖 |
| **容错解析** | 用户代码常处于不完整状态 | 参考 SQL Prompt 的 error recovery 策略 |
| **大数据库性能** | 数千张表时缓存更新慢 | 延迟加载 + 按需加载（只缓存活跃 schema） |
| **SSMS 扩展 API** | 需要深入理解 VS Shell 编辑器 API | 参考 MEF 导出 `ICompletionSourceProvider` |

### 5.3 最小可行实现（MVP）

```
阶段1（核心）：表名/列名补全
  - T-SQL 轻量解析器（仅解析 SELECT/FROM/WHERE 骨架）
  - 从 INFORMATION_SCHEMA 加载当前库的 schema
  - 简单的 FROM 后=表名 / SELECT 后=列名 规则
  - 候选列表按字母排序

阶段2（增强）：上下文感知 + 排序
  - 完善解析器支持更多语句类型
  - LRU 历史权重排序
  - JOIN 补全支持

阶段3（高级）：全功能补全
  - 存储过程参数提示
  - 函数签名提示
  - 链接服务器支持
  - 自定义配置
```
