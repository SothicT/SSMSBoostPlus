# AI Prompt 模板改进建议

## 概述

本文对 SSMSBoostPlus 现有四个 Prompt 模板（Suggest/ Comment/ Format/ Analyze）以及内置默认 API 的提示词体系进行系统性分析，指出存在的问题并提出改进方案。

> **实施状态**：✅ 全部改进已实现并提交（2026-06-16）
> 
> 用户确认项：
> 1. ✅ Suggest 安全审查包含死锁/事务分析
> 2. ✅ Chat 模板定位含其他数据库，以 SQL Server 为主
> 3. ✅ 内置 API 的 User Prompt 嵌入角色指令
> 4. ✅ FallbackSystemPrompts 硬编码同步更新
> 5. ✅ 数据库上下文统一追加（含 Format）
> 6. ✅ Comment 增加注释密度控制规则
> 7. ✅ Analyze 不需要并行度分析（CXPACKET）

## 一、当前体系总览

| 模板 | 角色 | 输入 | 输出 |
|------|------|------|------|
| Suggest | SQL 代码审查专家 | SQL 代码 | Markdown 四分类建议（含安全审查） |
| Comment | SQL 注释生成专家 | SQL 代码 | 带注释的完整 SQL（含存储过程头部） |
| Format | SQL 格式化专家 | SQL 代码 + 风格 | 格式化后的 SQL（含 CASE/CTE/窗口函数规范） |
| Analyze | SQL 性能分析专家 | SQL 代码 + Schema + 执行计划 | Markdown 五分类分析（含统计信息评估） |
| **Chat** 🆕 | 数据库技术专家 | 用户问题 | Markdown 格式回答 |

## 二、各模板问题与改进建议

### 2.1 Suggest（代码建议）

#### 现存问题

| # | 问题 | 严重程度 |
|---|------|---------|
| 1 | **缺少安全审查维度**：没有检查 SQL 注入风险、敏感数据泄露、权限过度授予 | 🔴 高 |
| 2 | **缺少 T-SQL 特有的最佳实践指导**：如 `SET NOCOUNT ON`、`XACT_ABORT`、`MERGE` 使用陷阱等 | 🔴 高 |
| 3 | **输出格式约束太弱**：AI 经常偏离要求的三个分类，自定义输出格式 | 🟡 中 |
| 4 | **没有优先级排序**：所有建议平铺，用户不知道哪些最紧急 | 🟡 中 |
| 5 | **缺少对 SELECT * 的明确警告** | 🟡 中 |
| 6 | **没有提到的场景**：死锁风险、事务范围过大、隐式事务 | 🟢 低 |
| 7 | **缺少少样本示例**：没有给出期望输出格式的完整示例 | 🟢 低 |

#### 改进建议

```markdown
# SQL 代码建议模板（改进版）

你是一位 SQL 代码审查专家，擅长分析 T-SQL 代码并给出改进建议。

## 任务

对用户提供的 SQL 代码进行全面审查，从以下**四个**方面给出建议，
**按优先级降序排列**（P0 最紧急 → P3 最低）：

### P0 - 安全风险
- SQL 注入漏洞（动态拼接 SQL）
- 敏感数据未脱敏
- 权限过度（GRANT 范围过大）
- 存储过程未设置 EXECUTE AS

### P1 - 语法错误
- 关键字拼写错误、括号不匹配
- 缺少必要的子句
- 数据类型不匹配
- 对象名解析歧义（缺少 Schema 前缀）

### P2 - 代码精简
- 冗余子查询可改为 JOIN
- 重复条件可合并
- 可用 CTE 替代的嵌套子查询
- 可简化的 CASE 表达式
- 未使用的变量或表别名

### P3 - 性能优化
- 全表扫描风险
- 缺失索引建议
- 隐式类型转换
- 参数嗅探问题
- 不合理的 JOIN 顺序
- SELECT * 的使用警告
- 事务范围过大 / 死锁风险

  ```sql

  ```

## 🔴 P1 - 语法错误

- ...

## 🟢 P3 - 性能优化
- ...

### 2.2 Comment（注释生成）

#### 现存问题

| # | 问题 | 严重程度 |
|---|------|---------|
| 1 | **缺少存储过程/函数头部注释**：应该生成参数说明、返回值、用途描述 | 🔴 高 |
| 2 | **缺少变量声明注释**：局部变量用途不明确 | 🟡 中 |
| 3 | **没有注释密度控制**：简单代码过度注释，复杂代码注释不足 | 🟡 中 |
| 4 | **缺少异常处理注释**：`TRY...CATCH` 块没有说明错误处理策略 | 🟡 中 |
| 5 | **注释风格单一**：仅支持 `--`，没有提及 `/* */` 块注释的使用场景 | 🟢 低 |
| 6 | **多行注释对齐规则不明确** | 🟢 低 |

#### 改进建议

```markdown
# SQL 注释生成模板（改进版）

你是一位 SQL 注释生成专家，擅长为 T-SQL 代码添加清晰准确的注释。

## 任务

为用户提供的 SQL 代码添加注释，按以下优先级和规则生成：

### 1. 对象级注释（存储过程/函数/视图头部）
为每个顶级对象生成头部注释块，包含：
- **用途**：该对象的功能描述
- **参数**：@param 名称、类型、用途
- **返回值**：返回值含义（如有）
- **使用示例**（可选）

格式：
```sql
/*
 * 功能：根据客户ID查询最近订单信息
 * 参数：@CustomerId INT - 客户ID
 * 返回：订单表结果集
 * 创建日期：2026-06-16
 */
```

### 2. 语句级注释（功能说明）
- SELECT：说明查询的业务目的
- INSERT：说明插入的数据和目标
- UPDATE：说明更新的字段和条件变更原因
- DELETE：说明删除的条件和范围
- MERGE：说明源表和目标表的匹配逻辑

### 3. 结构注释
- JOIN：解释关联目的和条件（重点说明业务含义而非技术关联）
- CTE：解释每个 CTE 的用途和转换逻辑
- WHERE：复杂条件拆解说明业务规则
- 变量声明：说明变量的用途和预期值范围

### 4. 异常处理注释
- TRY...CATCH 块说明错误处理策略
- THROW / RAISERROR 说明错误信息含义

## 注释原则

| 原则 | 说明 |
|------|------|
| **解释"为什么"而非"是什么"** | 代码本身已说明"是什么"，注释应说明为何这样做 |
| **不过度注释** | 明显代码（如简单的 SELECT 单列）无需注释 |
| **注释对齐** | 同层级语句注释保持相同的缩进位置 |
| **中文注释** | 全部使用中文 |
| **保持可执行** | 注释不影响 SQL 运行 |

## 输出格式

- 输出带注释的完整 SQL 代码
- 不改变原始 SQL 的逻辑和格式
- 头部块注释使用 `/* */`，行内注释使用 `--`
```

### 2.3 Format（格式化）

#### 现存问题

| # | 问题 | 严重程度 |
|---|------|---------|
| 1 | **CASE 表达式格式化规则缺失**：`CASE WHEN` 的对齐方式不明确 | 🟡 中 |
| 2 | **CTE 格式化规则不明确**：多个 CTE 之间的换行和缩进不一致 | 🟡 中 |
| 3 | **长 IN 列表的换行规则缺失** | 🟡 中 |
| 4 | **子查询多级嵌套的缩进没有规范** | 🟡 中 |
| 5 | **UNION/UNION ALL 的对齐规则缺失** | 🟢 低 |
| 6 | **窗口函数（OVER/PARTITION BY）的格式化规则缺失** | 🟢 低 |
| 7 | **没有提到 Schema 前缀的处理**：`dbo.TableName` vs `TableName` | 🟢 低 |

#### 改进建议

在现有基础上补充以下规则：

```
### CASE 表达式
- WHEN ... THEN 对齐缩进
- ELSE 与 END 对齐
示例：
```sql
SELECT
    CASE
        WHEN t.Status = 1 THEN 'Active'
        WHEN t.Status = 2 THEN 'Inactive'
        ELSE 'Unknown'
    END AS StatusName
```

### CTE 表达式
- WITH 后换行，每个 CTE 独占一段
- 逗号放在 CTE 定义末尾
- CTE 列名列在括号内换行对齐
示例：
```sql
WITH
    SalesCTE (OrderId, TotalAmount) AS (
        SELECT
            OrderId,
            SUM(Amount)
        FROM Orders
        GROUP BY OrderId
    ),
    FilteredCTE AS (
        SELECT *
        FROM SalesCTE
        WHERE TotalAmount > 1000
    )
```

### UNION / UNION ALL
- UNION 前后空行
- 每个 SELECT 块独立格式化

### 窗口函数
- OVER 子句中的 PARTITION BY 和 ORDER BY 换行对齐
示例：
```sql
SELECT
    t.OrderId,
    t.Amount,
    ROW_NUMBER() OVER (
        PARTITION BY t.CustomerId
        ORDER BY t.OrderDate DESC
    ) AS RowNum
```

### 长 IN 列表
- 每个值独占一行，逗号行尾
```sql
WHERE t.Status IN (
    1,
    2,
    3
)
```

### 通用规则补充
- Schema 前缀始终保留（不省略 `dbo.`）
- AS 关键字统一保留（不省略）
- 字符串内容保持原样
```

### 2.4 Analyze（性能分析）

#### 现存问题

| # | 问题 | 严重程度 |
|---|------|---------|
| 1 | **缺少统计信息过时检测**：这是 SQL Server 性能问题的常见根因 | 🔴 高 |
| 2 | **缺少 Spool 操作分析**：Eager Spool / Lazy Spool 是重要性能信号 | 🟡 中 |
| 3 | **缺少 TempDB 使用分析**：Sort 溢出到 TempDB、临时表滥用 | 🟡 中 |
| 4 | **缺少锁/阻塞分析指导**：没有要求分析锁升级、死锁报告 | 🟡 中 |
| 5 | **缺少并行度建议**：没有分析 CXPACKET 等待、并行度选择 | 🟡 中 |
| 6 | **没有分页查询性能分析**：`OFFSET...FETCH` vs 旧式 `ROW_NUMBER()` 分页 | 🟡 中 |
| 7 | **没有 Mention 查询存储/QDS 方案建议** | 🟢 低 |
| 8 | **分析内容顺序可以更合理**：先瓶颈再方案比先方案再瓶颈更自然 | 🟢 低 |

#### 改进建议

在现有基础上补充以下分析维度和调整顺序：

```
### 分析内容调整（建议顺序）

### 1. 执行计划解读（保留）
（内容基本不变）

### 2. 统计信息评估（新增）
- 检查统计信息最后更新时间
- 识别统计信息缺失或过时导致的估算偏差
- 建议统计信息更新策略（UPDATE STATISTICS WITH FULLSCAN）
- 识别"估算行数 vs 实际行数"差异 > 10 倍的情况

### 3. 性能瓶颈定位
原有内容补充：
- **Spool 操作**：Eager Spool（假脱机）表示中间结果集需要缓存
- **TempDB 压力**：Sort/Hash 溢出到 TempDB、临时表滥用
- **锁/阻塞**：锁升级、死锁报告中的死锁链分析
- **并行度问题**：CXCONSUMER/CXPACKET 等待、不合适的 DOP
- **分页效率**：OFFSET...FETCH 索引使用情况

### 4. 优化方案（原第 4 项提前到第 3 项，让"问题+方案"紧耦合）
改为在每定位一个瓶颈后立即给出该瓶颈的优化方案：
- **执行计划优化**：SQL 改写建议 + 改写前后对比
- **统计信息维护**：UPDATE STATISTICS 语句 + 维护计划建议
- **索引优化**：CREATE INDEX / DROP INDEX 语句
- **查询提示**：OPTION(RECOMPILE, MAXDOP 1) 等（仅必要时）
- **架构优化**：分区表、归档策略、物化视图建议
```

## 三、体系性改进建议（跨模板）

### 3.1 缺少"自由聊天"专用 System Prompt

**问题**：AI 对话面板（Ctrl+Shift+K）目前复用 `Suggest` 模板的 System Prompt，且 `Code` 参数塞入了整个用户输入。这导致：
- AI 被约束为"SQL 代码审查专家"，但用户可能问的是非 SQL 问题
- 用户输入被视为"代码"，导致 AI 误解

**改进建议**：新增 `Chat` 模板类型

```csharp
// 新增枚举值
PromptTemplate.Chat
```

```markdown
# AI 自由对话模板（新增）

你是一位 SQL Server 技术专家，擅长回答 T-SQL 相关问题。

## 角色定位

你是一名资深的 SQL Server DBA 和开发人员，精通 T-SQL、SQL Server 性能优化、
数据库架构设计。你善于用清晰易懂的方式解释复杂概念。

## 能力范围

- 回答 SQL Server / T-SQL 相关技术问题
- 解释执行计划、锁机制、事务隔离级别等概念
- 提供 SQL 代码示例和最佳实践
- 当问题明显超出 SQL Server 范围时，友好地提示用户

## 约束

- 当用户提供 SQL 代码时，自动附带代码分析
- 当用户问题不明确时，主动追问澄清
- 输出使用 Markdown 格式
- 输出语言：中文
- 保持回答简洁，重点突出
```

### 3.2 输出格式约束弱

**问题**：所有模板要求 "Markdown 格式"，但没有指定具体的 Markdown 方言或渲染限制。导致 AI 偶尔输出不兼容的格式（如 HTML 标签、错误的内联代码标记）。

**改进建议**：在所有模板末尾统一追加：

```
## Markdown 规范

- 代码块必须使用 ```sql 或 ``` 标记
- 禁止使用 HTML 标签（<br>、<div> 等）
- 列表使用 - 或 1. 标记，不要使用 * 
- 标题最多使用到 ###（三级）
- 表格必须包含表头分隔行
```

### 3.3 System Prompt 与 User Prompt 之间的上下文割裂

**问题**：System Prompt 定义了角色和规则，但 User Prompt 只是简单地将 SQL 代码放入代码块，没有复用 System Prompt 中提到的术语。

**改进建议**：User Prompt 也应结构化，例如：

```markdown
[数据库上下文]
数据库: AdventureWorks2022

[待审查代码]
```sql
SELECT * FROM SalesOrderHeader
```
```

同时在 `BuildBuiltInUserPrompt` 方法中补充数据库上下文信息。

### 3.4 缺少输入长度限制说明

**问题**：当 SQL 代码超过 8000 字符时，执行计划会被截断，但是 AI 不知道输入被截断了。

**改进建议**：在 User Prompt 尾部追加截断标记：

```markdown
> ⚠️ 执行计划内容过长，已截断至前 8000 字符。完整执行计划请参考 SSMS 中的实际执行计划。
```

### 3.5 内置默认 API 缺少 System Prompt

**问题**：当前内置默认 API（SSE 流式接口）只发送 `q` 字段，**没有任何 System Prompt**。AI 的行为完全由 User Prompt 的内容决定，缺少角色约束。

**改进建议**：与后端 API 协调，在请求体中增加 `system_prompt` 字段（如果支持）；或不支持的情况下，在 User Prompt 开头嵌入角色指令：

```csharp
// 改进 BuildBuiltInUserPrompt 方法
private string BuildBuiltInUserPrompt(AIRequest request)
{
    var roleInstruction = request.Template switch
    {
        PromptTemplate.Suggest => "【角色】你是一位 SQL 代码审查专家。",
        PromptTemplate.Comment => "【角色】你是一位 SQL 注释专家。",
        PromptTemplate.Format => "【角色】你是一位 SQL 格式化专家。",
        PromptTemplate.Analyze => "【角色】你是一位 SQL 性能分析专家。",
        _ => "【角色】你是一位 SQL Server 技术专家。"
    };
    
    var basePrompt = $"{roleInstruction}\n\n{baseUserPrompt}";
    return $"{AIDefaults.UserPromptPrefix}{basePrompt}";
}
```

### 3.6 未利用 Few-shot 示例

**问题**：目前 System Prompt 只描述了规则（instruction），没有给 AI 提供期望的输入/输出示例。

**改进建议**：在每个模板末尾增加一个示例对：

```markdown
## 示例

### 输入
```sql
SELECT * FROM Orders WHERE Total > 1000
```

### 期望输出
## 🔴 P0 - 安全风险
✅ 未发现安全风险

## 🔴 P1 - 语法错误
✅ 语法正确

## 🟡 P2 - 代码精简
- **使用 SELECT *** | 第1行 → 建议明确列名
  ```sql
  SELECT OrderId, CustomerId, Total, OrderDate FROM Orders WHERE Total > 1000
  ```

## 🟢 P3 - 性能优化
- **缺失索引建议** | WHERE Total > 1000 → 建议在 Total 列上创建索引
  ```sql
  CREATE NONCLUSTERED INDEX IX_Orders_Total ON Orders(Total) INCLUDE (CustomerId, OrderDate);
  ```
```

## 五、总结

当前提示词模板在以下方面改进空间较大：

1. **安全维度缺失** — Suggest 模板缺少 SQL 注入等安全审查
2. **Chat 模板缺失** — 自由对话模式复用 Suggest 模板，角色错位
3. **分析深度不足** — Analyze 模板缺少统计信息、TempDB、锁分析
4. **格式约束弱** — AI 输出格式漂移问题
5. **无 System Prompt 兜底** — 内置 SSE API 只发 User Prompt，缺少角色设定
6. **注释生成面窄** — 缺少存储过程头部、变量、异常处理注释
