# Issue Tracker — 测试问题追踪与修复工作流

本 Skill 提供一套轻量的 Issue 追踪工作流，与人工记录和 error-diagnosis 诊断能力协作，覆盖问题从记录到归档的全生命周期。

## 文件布局

```
docs/待处理问题箱.md                    <- 收件箱（人工记录，拆分后标记 `- [x]` 并记录时间，不清空）
AIDoc/问题修复/
  ├── 活跃/
  │   └── YYYY-MM-DD-序号-分类词.md      <- 独立问题文件（未闭环）
  └── 归档/
      ├── INDEX.md                       <- 归档索引
      └── YYYY-MM-DD-序号-分类词.md      <- 已关闭问题
```

## 核心概念

- 收件箱：`docs/待处理问题箱.md`，极简 checkbox 待办清单，人工维护。拆分后标记 `- [x]` 并记录拆分时间，不清空条目。
- 问题文件：`AIDoc/问题修复/活跃/YYYY-MM-DD-序号-分类词.md`，YAML frontmatter + 结构化正文，承载完整追踪信息。
- 状态流转：`待处理 -> 修复中(substep) -> 待确认 -> 已关闭`，含 `修复受阻` 回退路径。
- 修复中子步骤(substep)：`开始诊断 | 诊断完成 | 实施修复 | 编译验证 | 测试验证 | 修复完成`，用于中断恢复。
- 细化标记(refined)：`true | false`，标记问题是否已完成细化澄清。`false` 时开始修复会触发细化检查 Gate。
- 优先级：`紧急 | 阻断 | 高 | 中(默认) | 低`，问题概览时按优先级降序。紧急优先于阻断。
- 问题类型：`Bug | 新需求 | 优化`，从收件箱 `[类型]` 标签解析，写入 frontmatter `type` 字段。
- 标签(tags)：可选，逗号分隔，用于关联需求族，如 `版本历史页签, 连接信息`。
- 关闭原因：`已修复 | 无法复现 | 设计如此 | 暂不修复`，关闭时写入 frontmatter `resolution`（仅枚举值），具体修复方案写入正文「修复方案」章节。
- 时间线：问题文件 frontmatter 记录 `created`（提出/拆解时间）、`updated`（更新时间）、`closed`（关闭/归档时间），修复记录表格记录各阶段时间戳；收件箱中已拆分条目标记 `（已拆分于 YYYY-MM-DD）`。
- 诊断审查 Gate：error-diagnosis 输出诊断结果后必须停下，等待用户明确「开始修复」才能继续实施代码修改。

## 触发与能力

| 能力 | 触发词示例 | 说明 |
|------|-----------|------|
| 扫描拆分 | 扫描待处理问题箱 / 拆分问题 | 读取收件箱 -> 每个未处理条目生成独立文件 -> 标记 `- [x]`（不清空），自动评估是否需要细化 |
| 细化澄清 | 细化 xxx / 澄清 xxx | 按类型（Bug/新需求/优化）引导用户补充细节，填写 refined=true |
| 问题概览 | 问题进度 / 当前问题统计 | 扫描 AIDoc/问题修复/，按状态+优先级汇总，含归档统计 |
| 开始修复 | 修复 历史版本检索失败 / 处理问题三 | 加载文件 -> 细化检查Gate -> (Bug: error-diagnosis -> 诊断审查Gate) -> 实施修复 -> 编译+测试验证 |
| 确认归档 | 确认归档 xxx / 确认归档 全部 | 状态->已关闭，归档，更新 INDEX.md。裸「确认」/「归档」不触发，给出友好提示 |
| 继续修复 | 继续修复 xxx | 推进修复流程到下一步（如跳过诊断审查继续实施） |
| 暂停修复 | 暂停修复 xxx (原因) | 标记为「修复受阻」，保留已做工作 |
| 重新评估 | 重新评估 xxx | 从「修复受阻」回退到「待处理」 |
| 手动状态 | 标记 xxx 为暂不修复 | 跳过修复直接关闭归档 |
| 清理归档 | 清理归档 | 批量归档已关闭/待确认但未归档的问题 |
| 重建索引 | 重建归档索引 | 扫描归档目录重新生成 INDEX.md |

## 工作流

### 1. 扫描拆分

```
读取 docs/待处理问题箱.md
  -> 解析所有 `- [ ]` 条目，提取 `[优先级]`、`[类型]`（可选，默认 Bug）与描述（无优先级默认 中；支持全角「—」和半角「--」两种分隔符）
  -> 去重：
      · 提取简短描述（分隔符之前的部分）
      · 遍历 AIDoc/问题修复/ 下现有文件（含归档），读取 frontmatter 中的 `# {{TITLE}}`
      · 忽略大小写/标点/空格，使用 Levenshtein 距离 ≤ 3 或包含关系的模糊匹配
      · 命中已有文件 → 输出警告，让用户确认是否跳过
  -> 每个条目：
      · 文件名规则：
          1. 序号：当天日期下按拆分顺序递增，3 位补零（001, 002, ...）
          2. 分类词：AI 从描述中提取 2-4 个核心词，总长≤15 字符，用连字符连接
          3. 提取原则：保留模块名+核心动作/对象，去掉无意义词（如"时""的""了""需要""页面""鼠标"）
          4. 移除非法字符：\ / : * ? " < > |
          5. 若匹配到已有文件（文件名不同但标题相似），跳过序号
      · 最终文件名：{今日日期}-{序号}-{分类词}.md
      · 用 references/issue-template.md 模板生成，填充 status=待处理, priority, type, created
      · 正文「现象」取自条目描述，「涉及模块」如有则填
  -> 标记已拆分的 `- [ ]` 条目为 `- [x]`，行尾追加 `（已拆分于 YYYY-MM-DD）`，保留条目与结构
  -> 每个生成的问题文件，自动评估是否需要细化：
      · Bug 类：检查「现象」是否包含复现步骤（至少一个动作描述）和期望行为（至少一个对比描述）
        - 满足 → refined: true
        - 不满足 → refined: false，输出提示该问题建议细化
      · 新需求/优化类：始终 refined: false，输出提示建议细化
  -> 输出：拆分 N 个，跳过 M 个，细化建议 K 个，并列出生成的文件名
```

### 2. 问题概览

```
扫描 AIDoc/问题修复/活跃/ 下所有 .md
  -> 解析每个文件 frontmatter 的 status / priority / type / updated
  -> 按 status 分组，组内按 priority 降序（紧急>阻断>高>中>低）
  -> 另统计 归档/INDEX.md 中已关闭数量
  -> 输出表格 + 各问题一行卡片（文件名 | 状态 | 优先级 | 类型 | 更新时间）
```

### 3. 细化澄清

```
触发：「细化 xxx」或「澄清 xxx」
  -> 定位目标问题文件（模糊匹配文件名/描述）
  -> 读取 frontmatter 的 type 和 refined 字段
  -> 若 refined=true：提示「该问题已完成细化」，展示现有内容，询问是否需要修改

  === Bug 类型细化 ===
  -> 逐个提问（每次 1-2 个，用户可回答「跳过」）：
     Q1: 该 Bug 的复现步骤是什么？（从什么操作开始，到看到什么错误结束）
     Q2: 期望的正确行为是什么？（和当前错误行为对比）
     Q3: 影响范围是什么？（特定版本？特定数据库？所有用户？）
     Q4: 是否有相关的日志或错误信息？
  -> 将用户回答整理后写入：
     · 「现象」章节：补充复现步骤 + 期望行为
     · 「影响范围」章节：补充具体范围
     · 「涉及模块」章节：补充可能的模块
  -> 修改 frontmatter：refined: true, refined_at: 当日, updated: 当日
  -> 输出：「问题 xxx 已细化，可回复『开始修复 xxx』继续。」

  === 新需求类型细化 ===
  -> 逐个提问（每次 1-2 个，用户可回答「跳过」）：
     Q1: 这个需求解决什么用户场景？（谁、在什么情况下、想做什么）
     Q2: 完成后的验收标准是什么？（怎样算"做好了"）
     Q3: 是否有设计约束？（UI 风格、兼容性、性能要求等）
     Q4: 是否需要拆分为子任务？（复杂需求建议拆解）
  -> 将用户回答整理后写入：
     · 「需求澄清」章节：用户故事 + 验收标准 + 设计约束
     · 「现象」章节：补充需求背景
     · 「影响范围」章节：补充涉及的功能区域
  -> 修改 frontmatter：refined: true, refined_at: 当日, updated: 当日
  -> 输出：「问题 xxx 已细化，可回复『开始修复 xxx』继续。」

  === 优化类型细化 ===
  -> 逐个提问（每次 1-2 个，用户可回答「跳过」）：
     Q1: 当前的行为是什么？哪里不满意？
     Q2: 期望的改进效果是什么？（更快？更准确？更好看？）
     Q3: 如何衡量改进是否成功？（有量化指标最好）
     Q4: 优化的范围边界是什么？（只改某处，还是全线调整？）
  -> 将用户回答整理后写入：
     · 「需求澄清」章节：当前行为 + 期望行为 + 度量指标
     · 「现象」章节：补充优化背景
     · 「影响范围」章节：补充范围边界
  -> 修改 frontmatter：refined: true, refined_at: 当日, updated: 当日
  -> 输出：「问题 xxx 已细化，可回复『开始修复 xxx』继续。」
```

### 4. 开始修复（子步骤化流程）

```
Step A — 锁定问题
  解析用户意图中的目标问题（模糊匹配文件名/描述，或「问题三」=概览列表第3项）
  -> 读取问题文件，确认 status=待处理
  -> 修改 frontmatter：status=修复中, substep=开始诊断, updated=今日
  -> 向「修复记录」追加一行：当前时间 | 开始修复 | 涉及文件暂空 | 开始诊断

Step A.5 — 细化检查 Gate【条件性 Gate】
  -> 读取 frontmatter 的 refined 字段
  -> 若 refined = true：
      直接进入 Step B（Bug 类→ error-diagnosis；新需求/优化类→ 跳过 Step B+C，直接进入 Step D）
  -> 若 refined = false：
      输出细化引导框：

      ┌─ 问题尚未细化 ─────────────────────────────────────┐
      │ 当前问题描述较简略，直接修复可能导致方向偏差。         │
      │                                                      │
      │ Bug 类需要补充：复现步骤、期望行为、影响环境           │
      │ 新需求类需要补充：用户故事、验收标准、设计约束          │
      │ 优化类需要补充：当前行为、期望行为、度量指标            │
      │                                                      │
      │ 回复「细化 xxx」进入细化流程。                        │
      │ 回复「跳过细化」直接继续（风险自负）。                  │
      │ 回复「暂停修复 xxx (原因)」标记为修复受阻。              │
      └──────────────────────────────────────────────────────┘

      等待用户选择：
      - 「细化 xxx」→ 进入「3. 细化澄清」流程
      - 「跳过细化」→ 标记 refined: true（跳过标记），继续进入 Step B
      - 「暂停修复 xxx」→ 进入修复受阻流程

Step B — 调用 error-diagnosis（仅 Bug 类）
  若 type=新需求 或 type=优化：
    -> 跳过 Step B 和 Step C，直接进入 Step D（实施代码修复）
    -> 向「修复记录」追加一行：当前时间 | 跳过诊断 | - | 新需求/优化类型无需 error-diagnosis
  若 type=Bug：
    -> 若「诊断记录」区域为 `_待诊断_` 或空：
    -> 调用 error-diagnosis Skill，输入 = 问题 `type` + 「现象」+「涉及模块」
    -> 将诊断结果（根因/修复建议/涉及源码）完整写入「诊断记录」区域
  -> 修改 frontmatter：substep=诊断完成
  -> 向「修复记录」追加一行：当前时间 | 诊断完成 | 涉及文件暂空 | 写入诊断记录

Step C — 🛑 诊断审查 Gate【必须人工确认】
  在「诊断记录」写入后**停下**，向用户呈现诊断摘要：

  ┌─ 诊断结果待审查 ─────────────────────────┐
  │ 根因: <概括一句话>                        │
  │ 位置: src/xxx/xxx.cs:NN                  │
  │ 建议方案: <简短说明>                       │
  │ 详细诊断已写入问题文件。                   │
  │ 请确认是否按此方向修复。                   │
  │ 回复「开始修复」继续。                     │
  │ 回复「暂停修复 xxx (原因)」标记为修复受阻。  │
  └──────────────────────────────────────────┘

  用户回复「开始修复」→ 进入 Step D（同时更新 substep=实施修复）
  用户回复「暂停修复 xxx (原因)」→ 进入「修复受阻」流程

Step D — 实施代码修复
  -> 基于诊断结果与项目知识，引导并实施代码修复
  -> 记录修改涉及的文件路径列表
  -> 修改 frontmatter：substep=编译验证
  -> 向「修复记录」追加一行：当前时间 | 实施修复 | src/xxx.cs, src/yyy.cs | <修复要点>

Step E — 编译验证
  -> 执行：dotnet build SSMSBoostPlus.slnx -c Release
  -> 编译失败：
      · 修复编译错误
      · 向「修复记录」追加一行：当前时间 | 修复编译错误 | <修正的文件> | <错误描述>
      · 重试 Step E
  -> 编译通过 → 修改 frontmatter：substep=测试验证 → 进入 Step F

Step F — 测试验证
  -> 执行：dotnet test tests/SSMSBoostPlus.Tests/SSMSBoostPlus.Tests.csproj -c Release --no-build
  -> 测试失败：
      · 分析失败用例
      · 若为修复引入的回归 → 修正代码
      · 若为测试用例预期需更新 → 更新测试
      · 向「修复记录」追加一行
      · 重试 Step E+F
  -> 测试通过 → 进入 Step G

Step G — 提示 Regression Test
  -> 提示用户：「是否需要为此修复新增 Regression Test？（修复逻辑变更建议添加）」
  -> 如需添加，协助编写测试并等待用户确认测试通过
  -> 修改 frontmatter：status=待确认, substep=修复完成, updated=今日
  -> 将修复方案写入「修复方案」章节
  -> 向「修复记录」追加一行：当前时间 | 修复完成 | <涉及文件> | 编译测试通过
  -> 提示用户：「修复已完成，编译和测试已通过。请在环境中验证，确认无误后回复『确认归档 xxx』」。
```

### 5. 确认归档

```
用户回复「确认归档 xxx」（必须携带目标问题标识）或「确认归档 全部」
  -> 读取目标问题文件
  -> 若为「确认归档 全部」且待确认问题 > 1 个：
      · 输出列表并请求二次确认：「确认归档所有 N 个待确认问题？」
      · 用户确认后才执行
  -> 若待确认问题 = 1 个且用户未指定目标，直接操作该文件
  -> 若待确认问题 > 1 个且用户未指定目标，列出清单让用户选择目标
  -> 修改 frontmatter：status=已关闭, resolution=<关闭原因枚举值>, closed=今日, updated=今日
  -> 移动文件到 AIDoc/问题修复/归档/
  -> 向 归档/INDEX.md 追加一行（日期 | 问题 | 优先级 | 关闭原因）
  -> 输出归档结果

注意：裸「确认」/「归档」不再触发任何归档行为。若用户输入「归档」但未完整匹配：
  -> 扫描当前可归档的问题（status=待确认 或 status=已关闭 但未归档）
  -> 输出友好提示，引导用户使用「确认归档 全部」或「确认归档 <问题标识>」
```

### 6. 手动状态（兜底）

```
「标记 xxx 为暂不修复」/「标记 xxx 为无法复现」等
  -> 修改 frontmatter：status=已关闭, resolution=用户指定, closed=今日
  -> 执行与 5 相同的归档流程
```

### 7. 修复受阻与重新评估

```
触发条件：
  - Step C 中用户否定诊断结果，回复「暂停修复 xxx (原因)」
  - Step E/F 中遇到无法解决的阻塞
  - 用户直接回复「暂停修复 xxx (原因)」

修复受阻流程：
  -> 读取问题文件
  -> 修改 frontmatter：status=修复受阻, substep=(清空), updated=今日
  -> 向「修复记录」追加一行：当前时间 | 修复受阻 | - | <受阻原因>
  -> 输出「问题已标记为修复受阻，可回复『重新评估 xxx』回退到待处理」

重新评估流程：
  用户回复「重新评估 xxx」
  -> 修改 frontmatter：status=待处理, substep=(清空), updated=今日（保留已有的诊断记录和修复记录）
  -> 向「修复记录」追加一行：当前时间 | 重新评估 | - | 回退到待处理，准备重新诊断
  -> 输出「问题已回退到待处理，可重新开始修复」
```

### 8. 清理归档

```
扫描 AIDoc/问题修复/活跃/ 下所有 .md，筛选 status=已关闭 或 status=待确认 但未移入归档/ 的文件
  -> 对 status=待确认 的文件，先修改 status=已关闭, resolution=已修复, closed=今日
  -> 逐个执行归档流程（5）
  -> 输出清理结果
```

### 9. 重建归档索引

```
用户回复「重建归档索引」
  -> 扫描 AIDoc/问题修复/归档/ 下所有 .md（排除 INDEX.md）
  -> 逐个解析 frontmatter，提取：closed 日期, title, priority, resolution
  -> 按 closed 日期降序排序
  -> 重新生成 INDEX.md 的表格内容（保留文件头说明）
  -> 输出「归档索引已重建，共 N 条记录」
```

## 与 error-diagnosis 的协作

- 在「开始修复」的 Step B 中自动调用，**仅对 Bug 类型生效**。新需求/优化类型跳过诊断，直接进入实施修复。
- 输入来源：问题文件的 frontmatter `type` + 正文「现象」+「涉及模块」。
- 输出去向：写入问题文件的「诊断记录」区域，作为后续修复的依据。
- 若 error-diagnosis 命中知识库已有方案，直接采用；若为新问题类型，诊断结果作为新起点。
- **关键变化**：诊断完成后必须等待人工审查（Step C），不再自动进入修复。

## 注意事项

- 拆分前必须去重，**去重基于 frontmatter 标题做模糊匹配**（Levenshtein ≤ 3 或包含关系），命中时输出警告让用户确认。
- 文件名规则：`{YYYY-MM-DD}-{序号}-{分类词}.md`，序号 3 位补零，分类词从描述提取 2-4 个核心词（总长≤15 字符），移除非法字符（`\ / : * ? " < > |`）。
- 收件箱拆分后标记 `- [x]`，保留条目与结构，不清空。
- 归档索引 INDEX.md 必须随每次归档同步更新，保持可查。可通过「重建归档索引」修复索引不一致。索引中的「日期」列指归档日期（closed 字段值）。
- **归档动作不可逆**（已归档）。如误归档需手动从归档/移回，然后执行「重建归档索引」修复索引。
- 裸「确认」/「归档」不再触发归档。必须使用「确认归档 xxx」或「确认归档 全部」格式。
- 诊断审查 Gate 不可跳过——error-diagnosis 完成后必须等待用户「开始修复」指令。
- 修复后验证必须包含**编译 + 测试**两步，缺一不可。测试失败需分析原因并修正。
- 修改 frontmatter 时保持 YAML 格式合法，字符串无需引号（除非含特殊字符）。
- 涉及多文件修改时，修复记录「涉及文件」列需记录所有被修改的文件路径。
- 修复受阻回退到待处理时，保留已有诊断记录和修复记录，仅追加回退原因，不丢失历史。
- 问题概览按优先级排序：紧急 > 阻断 > 高 > 中 > 低。
- 问题文件 frontmatter 的 `status` 必须使用标准值（待处理/修复中/待确认/已关闭/修复受阻），禁止使用「已修复」等非标准值。
- 修复中子步骤通过 `substep` 字段追踪，中断后可从 substep 恢复而非重新开始。
- 收件箱条目格式：`- [ ] [优先级] [类型] 简短描述 — 补充说明`，类型标签可选，默认 Bug。
- 细化澄清不改变 status，仅修改 `refined` 和 `refined_at` 字段。细化内容写入问题文件正文对应章节。
- 细化检查 Gate（Step A.5）不可跳过细化逻辑，但允许用户选择「跳过细化」直接继续（风险自负，会记录跳过标记）。
- 新需求/优化类型不调用 error-diagnosis，细化澄清后直接进入实施修复阶段。
