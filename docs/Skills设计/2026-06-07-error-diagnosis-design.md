# 错误自动诊断工作流 — 设计文档

> 状态: 待评审 | 日期: 2026-06-07 | 版本: v1.0

---

## 1. 需求概述

建立一套 AI 辅助的自动化错误诊断工作流，能够根据日志中的报错信息，自动定位报错原因并给出修复方案。用户仅需提供错误日志，AI 完成：解析 → 分类 → 定位源码 → 根因分析 → 修复建议。

### 核心约束

| 维度 | 决策 |
|------|------|
| 触发方式 | A) 手动粘贴日志到 CodeBuddy + D) SSMS 右键"诊断最新日志" |
| 诊断深度 | 定位源码 + 根因分析 + 修复建议，**不自动修改代码**（人工决策修复） |
| 错误范围 | 运行时异常 + 编译错误 + 测试失败，统一入口自动分类分流 |
| 输出形式 | 对话中给摘要卡片（定位+原因），详细报告落盘 `AIDoc/诊断报告/` |
| IDE 数据源 | 右键自动读部署目录最新日志，提取 `[ERR]` / `[FTL]` 条目 |
| 知识积累 | `diagnosis/knowledge-base/` 渐进积累，三点匹配（异常类型+方法名+关键词） |

## 3. Skill 诊断工作流（7 步）

### Step 1: 解析 & 标准化

提取日志中的关键字段，支持三种输入格式：

| 来源 | 格式特征 | 提取字段 |
|------|----------|----------|
| Serilog 日志 | `{Timestamp} [{Level}] [{Machine}] {Message}{NewLine}{Exception}` | 时间戳、级别、机器名、消息、异常堆栈 |
| MSBuild 编译 | `error CSxxxx: message [file(line)]` | 错误码(CSxxxx)、消息、文件路径、行号 |
| xUnit 测试 | `Failed TestName [time]\nError Message: ...\nStack Trace: ...` | 测试名、失败消息、堆栈 |

### Step 2: 分类 & 分流

```
有 CSxxxx 编译码？ → build/ 分支
有 xUnit 失败标记？ → test/ 分支
有 Exception 堆栈？  → runtime/ 分支
多个错误混合？       → 逐个分诊，优先级: build > runtime > test
```

### Step 3: 知识库优先检索

对每个错误，查 `diagnosis/knowledge-base/{分类}/`，匹配规则：

```
三点中两点即命中:
  ① 异常类型完全相同
  ② 堆栈中出现"关键方法"
  ③ 错误消息包含"消息关键词"

优先级: 三点全中 > ①+② > ①+③ > ②+③

命中  → 跳 Step 6（直接输出已知方案）
未命中 → 继续 Step 4
```

### Step 4: 源码定位 & 上下文分析

从堆栈第一个项目代码帧（跳过系统/第三方框架帧）提取：
- 类名/方法名 → `search_content` 定位源文件
- 行号（如有）→ `read_file` 读上下文
- 分析调用链、参数来源、异常触发条件

### Step 5: 根因推理

综合异常类型 + 代码逻辑 + 项目架构约束，从以下维度推理：

| 场景 | 推理方向 |
|------|----------|
| 空引用 | 谁应负责初始化？是否漏了 Null 检查？ |
| 反射失败 | 类型名/方法名是否正确？程序集是否加载？ |
| 编译错误 | 缺少 using？缺少项目引用？版本不匹配？ |
| 测试失败 | 断言值来源？Mock 设置是否正确？ |

### Step 6: 生成修复建议

结构化输出 5 个部分：
1. **问题摘要**（一句话）
2. **根因分析**（为什么发生）
3. **修复方案**（具体代码改动建议 + 位置）
4. **预防措施**（如何避免再现）
5. **关联知识库条目**（如有）

### Step 7: 输出 & 归档

- **对话输出**: 摘要卡片（①+②+③精简版）
- **报告落盘**: `AIDoc/诊断报告/YYMMDD-HHMMSS-摘要.md`
- **知识归档**: `diagnosis/knowledge-base/{分类}/xxx.md`（仅新错误类型）

## 5. 知识库条目模板

```markdown
# [异常类型简称]

## 匹配特征
- 异常类型: `System.NullReferenceException`
- 关键方法: `GetConnectionString`
- 消息关键词: `Object reference not set`

## 常见根因
1. 原因A：xxx 未初始化就被调用
2. 原因B：xxx 返回 null 后未判空

## 修复方案
1. 方案A：在 xxx 方法开头添加 Null 检查 + 提前返回
2. 方案B：确保 xxx 在构造函数中完成初始化

## 预防措施
- 所有公共 API 入口加参数 Null 守卫
- 启用 `<Nullable>enable</Nullable>` 让编译器帮你查

## 关联源码
- `src/SSMS/Services/Connection/DatabaseConnectionHelper.cs:42`

## 历史案例
- 2026-06-07: 部署后首次启动报此错，原因是配置目录未创建
```

## 7. IDE 右键集成方案

```
SSMS 右键菜单 "诊断最新日志" 命令执行流程：

① 定位日志目录 → {部署目录}\Logs\
② 找最新 .log 文件 → 按修改时间降序
③ 提取所有 [ERR] / [FTL] 行 → 写入临时摘要文件
④ 弹出提示框 → "请在 CodeBuddy 中说「诊断最新日志」即可开始诊断"
⑤ Skill 读取临时摘要文件 → 开始 7 步诊断流程
```

> **设计理由**: SSMS 扩展进程与 CodeBuddy 进程隔离，无法直接通信。采用"写中间文件 + 用户确认"的桥接方式。

## 9. 边缘情况与异常处理

| 场景 | 处理 |
|------|------|
| 日志格式无法识别 | 提示用户确认输入类型，列出支持的三种格式 |
| 堆栈中没有项目代码帧 | 标记为"第三方/框架异常"，仅分析消息，不做源码定位 |
| 知识库匹配到多个条目 | 列出所有匹配，按匹配度排序，由用户选择 |
| 日志文件不存在 | 提示用户先触发一次错误或手动指定日志路径 |
| 多个错误混合输入 | 逐个分诊，按 build > runtime > test 排序输出 |
| 诊断超时（代码搜索过多） | 最多搜索 10 次，未定位则标记为"需人工分析" |
