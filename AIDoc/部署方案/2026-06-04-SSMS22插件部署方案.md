# SSMSBoostPlus 插件部署到 SSMS 22 — 五套可行方案

> 文档版本：v1.1 | 创建日期：2026-06-04 | 更新日期：2026-06-04 | 项目：SSMSBoostPlus

## 一、背景与前提知识

### 1.1 项目编译产物

SSMSBoostPlus 采用四项目结构，编译后产生以下关键文件：

| 文件名 | 来源项目 | 说明 |
|--------|---------|------|
| `SSMSBoostPlus.SSMS.dll` | src/SSMS (net472) | 主程序集（VsPackage 入口） |
| `SSMSBoostPlus.Core.dll` | src/Core (netstandard2.0) | 核心业务逻辑库 |
| `SSMSBoostPlus.AI.dll` | src/AI (netstandard2.0) | AI 功能模块（Bridge/Prompts/Services） |
| `SSMSBoostPlus.Shared.dll` | src/Shared (netstandard2.0) | 共享库（常量、枚举、扩展方法） |
| `*.pdb`（4个） | 各项目 | 调试符号（可选） |
| `SSMSBoostPlus.SSMS.pkgdef` | VSSDK 生成 | 注册表合并脚本 |
| `SSMSBoostPlus.cto` → `Menus.ctmenu` | VSCT 编译产物 | 命令表二进制资源 |
| `extension.vsixmanifest` | 源码清单复制 | VSIX 清单文件 |

**项目引用链**：SSMS → Core + AI → Core + Shared（AI 和 Core 都引用 Shared）

**输出目录**：`src\SSMS\bin\Release\net472`

**中间产物目录**（pkgdef/cto 所在）：`src\SSMS\obj\Release\net472`

### 1.2 第三方依赖项

以下 DLL 必须随主程序集一同部署到目标目录：

- `DiffPlex.dll` — SQL 差异对比引擎
- `Serilog.dll` — 日志框架
- `Serilog.Sinks.File.dll` — 文件日志输出
- `Serilog.Enrichers.Environment.dll` — 环境信息日志增强
- `Microsoft.Data.SqlClient.dll` — SQL Server 数据驱动
- `Newtonsoft.Json.dll` — JSON 序列化
- `System.Net.Http.dll` / `Microsoft.Bcl.AsyncInterfaces.dll` — 异步基础库
- `Microsoft.Extensions.Configuration.*.dll` — 配置框架（3个）
- `Microsoft.SqlServer.TransactSql.ScriptDom.dll` — T-SQL 解析器

### 1.3 目标部署路径

SSMS 22 的 VS 扩展安装目录结构如下：

```
D:\Program Files\Microsoft SQL Server Management Studio 22\
└── Release\
    └── Common7\
        └── IDE\
            └── Extensions\
                └── SSMSBoostPlus\          ← 主部署目录（本方案使用）
                    ├── SSMSBoostPlus.SSMS.dll
                    ├── SSMSBoostPlus.Core.dll
                    ├── SSMSBoostPlus.AI.dll
                    ├── SSMSBoostPlus.Shared.dll
                    ├── *.pdb（可选）
                    ├── *.pkgdef
                    ├── Menus.ctmenu
                    ├── extension.vsixmanifest
                    └── （依赖 DLL...）
            └── commonextensions\
                └── SSMSBoostPlus\          ← 冲突目录（需清理）
```

**关键配置触发机制**：
- 写入 `Extensions\extensions.configurationchanged` 文件可触发 SSMS 重启时重新扫描扩展目录
- 或运行 `ssms.exe /setup` 强制 PkgDef 合并到私有注册表（`privateregistry.bin`）

### 1.4 已知技术坑点（来自实际踩坑经验）

以下是本项目在 SSMS 22 部署过程中积累的关键经验，所有方案均须遵守：

1. **CTO 资源必须嵌入 DLL**：SSMS 通过 CFCT 魔术字节检测 CTO，若未嵌入会认为扩展无效并删除整个扩展目录。因此 `.cto` 既要作为嵌入式资源嵌入 DLL，又要以 `Menus.ctmenu` 文件形式放置在部署目录（双保险）。

2. **两阶段构建流程**：.NET SDK 的 MSBuild 中，Target 内动态 ItemGroup 添加的 EmbeddedResource 不生效。必须采用"第1次 build 生成 CTO → 第2次 build 将预生成的 CTO 嵌入 DLL"的两阶段构建。

3. **pkgdef GUID 一致性**：pkgdef 中注册的 GUID 必须与代码中 `[Guid("a1b2c3d4-e5f6-7890-abcd-ef1234567890")]` 完全一致，否则 VS Shell 无法定位包。

4. **CreatePkgDef.exe 崩溃问题**：VSSDK BuildTools 17.8 附带的 CreatePkgDef.exe 18.5.40034 在 `GeneratePkgDefFile=false` 时会抛出 ArgumentNullException，已改用 PowerShell 脚本模板直接生成 pkgdef。

5. **VSSDK 自动管道 7 处 Bug**：包括包名截断、`$WinDir*` / `$RootKey%` 子键符错误、多余 Assembly/ToolWindows 节、Menus 嵌入 ID 模式错误、AutoLoad 值错误等。当前项目已切换为手动管线绕过。

6. **PowerShell 变量转义冲突**：MSBuild Exec 内联调用 PowerShell 时，`$` 变量和引号会与 XML/cmd 解析冲突，必须将 PowerShell 逻辑抽取到外部 `.ps1` 脚本文件中执行。

7. **ssms.exe /setup 是必需步骤**：部署后必须运行此命令强制 PkgDef 重新扫描合并到私有注册表。私有注册表实际路径为 `HKU\<SID>\Software\Microsoft\SSMS\22.0_<hash>_Config\`（注意是 `_Config` 后缀，非 `_Configuration`）。

8. **EnvDTE 引用路径**：csproj 中 EnvDTE 的 HintPath 硬编码了 SSMS 安装目录，更换机器或 SSMS 版本时需同步修改。

## 二、方案一：手动批处理脚本部署（当前已有方案）

### 2.1 实现原理

通过 Windows Batch 脚本（`.bat`），将编译产物从输出目录（`bin\Release\net472`）手动复制到 SSMS 22 的 Extensions 目录。利用写入 `extensions.configurationchanged` 触发文件通知 SSMS 在下次启动时重新扫描扩展注册表。

### 2.2 当前脚本分析

现有 `deploy-to-ssms.bat` 已实现完整的 7 步部署流程：

```
Step 1: 检查编译产物是否存在（dll 缺失则中止）
Step 2: 清理冲突目录（commonextensions 下的同名目录）
Step 3: 创建/确认 Extensions\SSMSBoostPlus 目录
Step 4: 复制核心 DLL + PDB（含条件判断）
Step 5: 复制配置文件（pkgdef、cto→Menus.ctmenu、vsixmanifest，多路径回退）
Step 6: 复制第三方依赖项
Step 7: 写入 configurationchanged 触发配置刷新
```

### 2.3 使用方式

```bat
:: 前置条件
:: 1. dotnet build -c Release    （确保编译成功）
:: 2. 以管理员身份运行 deploy-to-ssms.bat
:: 3. 重启 SSMS 22
deploy-to-ssms.bat
```

### 2.4 优化建议

当前脚本的不足及改进方向：

| 问题 | 改进方案 |
|------|---------|
| 路径硬编码（PROJECT_DIR、SSMS_EXT_DIR） | 改为 `%~dp0` 相对路径 + 可选命令行参数覆盖 |
| 未运行 `ssms.exe /setup` | 增加 Step 8 调用 `/setup`（可选，因重启也可生效） |
| 无备份/回滚能力 | 部署前先将旧目录备份为 `SSMSBoostPlus.bak.<timestamp>` |
| 无版本校验 | 部署前对比 dll 版本信息，避免误部署旧版本 |
| 依赖项硬编码列表 | 改为 `xcopy /Y *.dll` 通配复制全部依赖 |

### 2.5 优缺点

**优点**：
- 实现最简单，无需额外工具链
- 每步可控，便于排查部署问题
- 已有现成脚本可直接使用
- 不修改 csproj，不影响编译流程

**缺点**：
- 路径硬编码，换机器需手动改
- 每次改代码需手动执行两步操作（编译+部署）
- 需要管理员权限（写 Program Files）
- 不适合分发他人

### 2.6 适用场景

日常开发调试、个人开发机、快速验证改动效果

## 三、方案二：VSIX 安装包部署（标准分发格式）

### 3.1 实现原理

利用 VSSDK BuildTools 的 VSIX 打包能力，将扩展及其依赖打包为一个 `.vsix` 文件（本质是 ZIP 格式）。VSIX 包含完整的清单声明、内容文件和数字签名信息，可通过 SSMS 扩展管理器安装，或通过命令行批量部署。

### 3.2 实施步骤

#### 步骤一：启用 VSIX 打包

修改 `src\SSMS\SSMSBoostPlus.SSMS.csproj`：

```xml
<!-- 将 false 改为 true -->
<CreateVsixContainer>true</CreateVsixContainer>
```

#### 步骤二：适配 CTO 嵌入与 pkgdef 生成

当前项目的 CTO 嵌入和 pkgdef 生成都被注释掉了（因 .NET SDK 兼容性问题切换到了手动管线）。启用 VSIX 打包前需要解决以下兼容性问题：

1. **恢复 CTO 嵌入 ItemGroup**（csproj 第72-77行取消注释）。但需要注意静态 ItemGroup 在首次编译时 cto 尚不存在的问题，建议改为两阶段构建脚本处理。

2. **pkgdef 生成**：由于 CreatePkgDef.exe 存在崩溃 bug，继续使用现有的 `generate-pkgdef.ps1` 模板生成方案，并在 csproj 中将 `<GeneratePkgDefFile>` 设为 `false`，改用手动 Target 调用 ps1 脚本。

3. **vsixmanifest Asset 声明**：当前 `source.extension.vsixmanifest` 中只声明了 `pkgdef` 类型的 Asset，VSIX 打包时可能需要补充 Menus.ctmenu 和 DLL 的 Asset 声明。

```xml
<Assets>
  <Asset Type="Microsoft.VisualStudio.VsPackage" d:Source="Project"
         d:ProjectName="SSMSBoostPlus.SSMS" Path="|SSMSBoostPlus.SSMS;" />
  <Asset Type="Microsoft.VisualStudio.Menus.Resource"
         Path="Menus.ctmenu" />
</Assets>
```

#### 步骤三：编译生成 VSIX

```bash
dotnet build src/SSMS/SSMSBoostPlus.SSMS.csproj -c Release
# 输出: src/SSMS/bin/Release/net472/SSMSBoostPlus.SSMS.vsix
```

#### 步骤四：安装方式

**方式 A — 双击安装**：直接双击 `.vsix` 文件，启动 VSIX Installer 向导

**方式 B — 命令行安装**：
```bash
# 安装
/ssms.exe /updateSource "path\to\SSMSBoostPlus.SSMS.vsix"

# 或使用 VSIXInstaller.exe（位于 SSMS 安装目录）
"Common7\IDE\VSIXInstaller.exe" "path\to\SSMSBoostPlus.SSMS.vsix"
```

**方式 C — 静默安装**（适合批量部署）：
```bash
VSIXInstaller.exe /quiet "path\to\SSMSBoostPlus.SSMS.vsix"
```

### 3.3 注意事项

- VSIX 安装后文件位于 `commonextensions` 目录（而非 `Extensions` 目录），这是 VSIX Installer 的标准行为
- VSIX 支持 CodeSign 数字签名，发布前应签名以确保用户安装时不出现安全警告
- 升级时 VSIX Installer 会自动处理旧版本卸载和新版本安装
- SSMS 的 InstallationTarget Id 为 `Microsoft.VisualStudio.Ssms`，Version `[17.0,)`（已正确配置）

### 3.4 优缺点

**优点**：
- Microsoft 标准 VS 扩展分发格式，官方支持
- 支持图形化安装/卸载/升级
- 可发布到 Visual Studio Marketplace 或内部共享
- 包含版本管理和依赖声明
- 安装过程自动处理注册表合并

**缺点**：
- 当前手动 VSSDK 管线与 VSIX 打包流程存在兼容性冲突，需要额外适配工作
- 打包调试周期比直接复制长（每次改动都要重新打包）
- VSIX Installer 对 AllUsers 安装需要管理员权限
- 开发阶段不如直接复制高效

### 3.5 适用场景

正式发布给团队或社区使用、需要版本管理和升级能力的场景、客户现场部署

## 四、方案三：MSBuild Post-Build 事件自动部署

### 4.1 实现原理

在 `SSMSBoostPlus.SSMS.csproj` 中定义一个 AfterBuild Target，当编译成功完成后自动将输出文件复制到 SSMS 22 的 Extensions 目录。实现"按 F5 编译即部署"的无缝开发体验。

### 4.2 实施步骤

#### 方式 A：使用 MSBuild Copy Target（推荐）

在 `SSMSBoostPlus.SSMS.csproj` 的 `</Project>` 前添加：

```xml
<!-- ========== 自动部署 Target ========== -->
<Target Name="DeployToSSMS" AfterTargets="Build" Condition="'$(Configuration)' == 'Release'">
    <!-- 定义属性 -->
    <PropertyGroup>
        <SsmsExtPath Condition="$(SsmsExtPath) == ''">D:\Program Files\Microsoft SQL Server Management Studio 22\Release\Common7\IDE\Extensions\SSMSBoostPlus</SsmsExtPath>
        <ConfigFlagPath>D:\Program Files\Microsoft SQL Server Management Studio 22\Release\Common7\IDE\Extensions\extensions.configurationchanged</ConfigFlagPath>
    </PropertyGroup>

    <!-- 1. 创建目标目录 -->
    <MakeDir Directories="$(SsmsExtPath)" />

    <!-- 2. 复制主程序集和核心DLL -->
    <Copy SourceFiles="$(TargetPath)" DestinationFolder="$(SsmsExtPath)" SkipUnchangedFiles="true" />
    <Copy SourceFiles="$(TargetDir)SSMSBoostPlus.Core.dll" DestinationFolder="$(SsmsExtPath)" SkipUnchangedFiles="true"
          Condition="Exists('$(TargetDir)SSMSBoostPlus.Core.dll')" />

    <!-- 3. 复制PDB（如果存在） -->
    <Copy SourceFiles="$(TargetDir)$(TargetName).pdb" DestinationFolder="$(SsmsExtPath)" SkipUnchangedFiles="true"
          Condition="Exists('$(TargetDir)$(TargetName).pdb')" />

    <!-- 4. 复制pkgdef -->
    <Copy SourceFiles="$(IntermediateOutputPath)$(TargetName).pkgdef"
          DestinationFolder="$(SsmsExtPath)"
          Condition="Exists('$(IntermediateOutputPath)$(TargetName).pkgdef')" />

    <!-- 5. 复制CTO为Menus.ctmenu -->
    <Copy SourceFiles="$(IntermediateOutputPath)SSMSBoostPlus.cto"
          DestinationFiles="$(SsmsExtPath)\Menus.ctmenu"
          Condition="Exists('$(IntermediateOutputPath)SSMSBoostPlus.cto')" />

    <!-- 6. 复制依赖DLL（通配） -->
    <ItemGroup>
        <DepDlls Include="$(TargetDir)\DiffPlex.dll" />
        <DepDlls Include="$(TargetDir)\Serilog*.dll" />
        <DepDlls Include="$(TargetDir)\Microsoft.Data.SqlClient.dll" />
        <DepDlls Include="$(TargetDir)\Newtonsoft.Json.dll" />
        <DepDlls Include="$(TargetDir)\Microsoft.Extensions.Configuration*.dll" />
        <DepDlls Include="$(TargetDir)\Microsoft.SqlServer.TransactSql.ScriptDom.dll" />
    </ItemGroup>
    <Copy SourceFiles="@(DepDlls)" DestinationFolder="$(SsmsExtPath)"
          SkipUnchangedFiles="true" Condition="Exists('%(DepDlls.Identity)')" />

    <!-- 7. 触发配置刷新 -->
    <WriteLinesToFile File="$(ConfigFlagPath)" Lines="$([System.DateTime]::Now.ToString())" Overwrite="true"
                       Encoding="UTF-8" />

    <!-- 输出提示 -->
    <Message Importance="high" Text="=========================================" />
    <Message Importance="high" Text="  ✅ Auto-deployed to SSMS 22!" />
    <Message Importance="high" Text="  Target: $(SsmsExtPath)" />
    <Message Importance="high" Text="  Please restart SSMS to load changes." />
    <Message Importance="high" Text="=========================================" />
</Target>
```

#### 方式 B：调用外部 PowerShell 脚本

如果部署逻辑更复杂（如备份、版本检查），可将具体逻辑放入外部 `.ps1` 脚本，PostBuild 仅负责调用：

```xml
<Target Name="DeployToSSMS" AfterTargets="Build" Condition="'$(Configuration)' == 'Release'">
    <Exec Command="powershell -ExecutionPolicy Bypass -File &quot;$(MSBuildProjectDirectory)\deploy-ps.ps1&quot; &quot;$(TargetDir)&quot; &quot;$(IntermediateOutputPath)&quot;"
          WorkingDirectory="$(MSBuildProjectDirectory)" IgnoreExitCode="true" />
</Target>
```

### 4.3 使用方式

```bash
# 只需正常编译即可自动部署
dotnet build src/SSMS/SSMSBoostPlus.SSMS.csproj -c Release

# 或在 Visual Studio 中按 Ctrl+Shift+B（Release 配置）
# 编译完成后 Output 窗口显示 "✅ Auto-deployed to SSMS 22!"
```

### 4.4 优缺点

**优点**：
- 开发效率最高：一次操作完成编译+部署
- 减少人为遗漏（忘记部署的情况不再发生）
- 利用 MSBuild 条件判断，可灵活控制何时触发
- `SkipUnchangedFiles="true"` 避免不必要的文件写入，加速增量构建

**缺点**：
- 需要 VS/命令行以管理员权限运行（写 Program Files 需要权限）
- 路径仍需硬编码（或改为 MSBuild Property 传入）
- 编译失败时不会部署（这其实也是优点，防止部署不完整产物）
- Debug 模式下通常不需要部署（可通过 Condition 限制仅 Release 触发）

### 4.5 适用场景

高频迭代的开发调试期、单人开发机日常使用

## 五、方案四：PowerShell 现代化部署脚本

### 5.1 实现原理

用 PowerShell 替代 Batch 脚本，充分利用其结构化错误处理、对象化文件系统操作、注册表查询能力，打造一个智能化部署工具。支持自动探测 SSMS 安装路径、参数化的子命令设计、部署前后备份回滚。

### 5.2 核心功能设计

```powershell
#.SYNOPSIS
#  SSMSBoostPlus 部署工具 v2.0
#.DESCRIPTION
#  支持 install / uninstall / status / backup 四种操作模式
#.EXAMPLE
#  .\deploy.ps1 -Action install
#  .\deploy.ps1 -Action uninstall
#  .\deploy.ps1 -Action status
#.PARAMETER Action
#  操作类型: install | uninstall | status | backup
#.PARAMETER SsmsPath
#  自定义 SSMS 安装路径（留空则自动探测）
#.PARAMETER SourceDir
#  自定义编译产物目录（留空则默认 bin/Release/net472）
```

### 5.3 关键实现要点

#### 自动探测 SSMS 安装路径

```powershell
function Resolve-SsmsInstallPath {
    # 方法1: 注册表查询（最可靠）
    $regPath = "HKLM:\SOFTWARE\Microsoft\Microsoft SQL Server\SSMS"
    if (Test-Path $regPath) {
        return (Get-ItemProperty $regPath).InstallLocation
    }

    # 方法2: 常见安装路径枚举
    $candidates = @(
        "${env:ProgramFiles}\Microsoft SQL Server Management Studio 22",
        "${env:ProgramFiles(x86)}\Microsoft SQL Server Management Studio 22",
        "D:\Program Files\Microsoft SQL Server Management Studio 22"
    )
    foreach ($c in $candidates) {
        if (Test-Path "$c\Release\Common7\IDE\ssms.exe") { return $c }
    }

    throw "无法自动探测 SSMS 22 安装路径，请使用 -SsmsPath 参数指定"
}
```

#### 部署前备份

```powershell
function Backup-CurrentDeployment {
    param([string]$TargetDir)
    if (Test-Path $TargetDir) {
        $timestamp = Get-Date -Format "yyyyMMdd_HHmmss"
        $backupDir = "$TargetDir.bak.$timestamp"
        Copy-Item -Path $TargetDir -Destination $backupDir -Recurse -Force
        Write-Host "[OK] 已备份到: $backupDir" -ForegroundColor Cyan
    }
}
```

#### 结构化文件复制

```powershell
$deployMap = [ordered]@{
    # 源文件(相对SourceDir) = 目标文件名
    "SSMSBoostPlus.SSMS.dll"                          = "SSMSBoostPlus.SSMS.dll"
    "SSMSBoostPlus.Core.dll"                           = "SSMSBoostPlus.Core.dll"
    "..\obj\Release\net472\SSMSBoostPlus.SSMS.pkgdef"  = "SSMSBoostPlus.SSMS.pkgdef"
    "..\obj\Release\net472\SSMSBoostPlus.cto"           = "Menus.ctmenu"
}

foreach ($entry in $deployMap.GetEnumerator()) {
    $src = Join-Path $SourceDir $entry.Key
    $dst = Join-Path $TargetDir $entry.Value
    if (Test-Path $src) {
        Copy-Item -Path $src -Destination $dst -Force
        Write-Host "[OK] $($entry.Value)" -ForegroundColor Green
    } else {
        Write-Host "[WARN] 缺失: $($entry.Key)" -ForegroundColor Yellow
    }
}
```

#### 权限自提升

```powershell
function Ensure-Admin {
    $identity = [Security.Principal.WindowsIdentity]::GetCurrent()
    $principal = New-Object Security.Principal.WindowsPrincipal($identity)
    if (-not $principal.IsInRole([Security.Principal.WindowsBuiltInRole]::Administrator)) {
        Write-Host "[INFO] 需要管理员权限，正在请求提升..." -ForegroundColor Yellow
        Start-Process powershell -ArgumentList "-NoProfile -ExecutionPolicy Bypass -File `"$PSCommandPath`"" -Verb RunAs -Wait
        exit
    }
}
```

### 5.4 完整命令接口

```powershell
# 安装（自动探测路径）
.\deploy.ps1 -Action install

# 安装（指定 SSMS 路径）
.\deploy.ps1 -Action install -SsmsPath "D:\Program Files\Microsoft SQL Server Management Studio 22"

# 卸载（清理部署目录并刷新配置）
.\deploy.ps1 -Action uninstall

# 查看当前部署状态（版本号、文件数量、最后更新时间）
.\deploy.ps1 -Action status

# 手动备份当前部署
.\deploy.ps1 -Action backup

# 安装后立即重启 SSMS
.\deploy.ps1 -Action install -Restart
```

### 5.5 优缺点

**优点**：
- 跨平台友好（PowerShell Core / PowerShell 7 兼容 Windows/macOS/Linux）
- 路径自适应（注册表探测 + 回退策略），换机器零配置
- 参数化设计，支持多种操作模式（install/uninstall/status/backup）
- 结构化错误处理和详细日志输出
- 支持权限自提升，避免"忘记以管理员运行"的低级错误
- 易于扩展新功能（如远程部署、多版本管理）

**缺点**：
- 执行策略限制（需 Bypass 或 RemoteSigned）
- 对不熟悉 PowerShell 的开发者有一定学习成本
- 单文件脚本较 bat 更复杂，维护成本略高

### 5.6 适用场景

多开发机环境、需要频繁在不同机器上部署、正式环境的运维部署

---

## 六、方案五：CI/CD 自动化部署

### 6.1 实现原理

将编译、打包、部署全流程集成到 CI/CD Pipeline 中，实现代码提交后全自动构建和部署。支持多环境（开发/测试/生产）、版本标签化管理、自动化测试门禁。

### 6.2 架构设计

```
Git Push / Tag
    ↓
GitHub Actions Trigger
    ├─→ .NET Build (Release)
    │     ├─ Restore NuGet
    │     ├─ Build Solution
    │     ├─ Run Unit Tests
    │     └─ Publish Artifacts (dll, pkgdef, vsix)
    ├─→ Package VSIX (可选)
    ├─→ Upload Artifact
    └─→ Deploy (可选)
          ├─ SSH/远程脚本推送到测试服务器
          └─ 或 Release 附件供手动下载
```

### 6.3 GitHub Actions Workflow 示例

```yaml
name: SSMSBoostPlus CI/CD

on:
  push:
    branches: [master, develop]
  workflow_dispatch:  # 手动触发

jobs:
  build:
    runs-on: windows-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup .NET SDK
        uses: actions/setup-dotnet@v4
        with:
          dotnet-version: '10.x'

      - name: Restore dependencies
        run: dotnet restore

      - name: Build Release
        run: dotnet build SSMSBoostPlus.sln -c Release --no-restore

      - name: Run Tests
        run: dotnet test tests/SSMSBoostPlus.Tests.csproj -c Release --no-build --verbosity normal

      - name: Package VSIX
        run: |
          # 如果启用 VSIX 打包，在此处收集产物
          mkdir artifact
          copy src\SSMS\bin\Release\net472\*.* artifact\
          # 打包为 zip 下载
          Compress-Archive -Path artifact\* -DestinationPath SSMSBuild.zip

      - name: Upload Build Artifacts
        uses: actions/upload-artifact@v4
        with:
          name: SSMSBuild-${{ github.sha }}
          path: artifact/
          retention-days: 30

  # 可选：创建 GitHub Release 并附加 VSIX
  release:
    needs: build
    if: startsWith(github.ref, 'refs/tags/v')
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v4
        with:
          name: SSMSBuild-${{ github.sha }}

      - name: Create Release
        uses: softprops/action-gh-release@v2
        with:
          files: SSMSBuild-*
          generate_release_notes: true
```

### 6.4 Azure Pipelines 变体

对于企业内网环境（无法访问 GitHub），Azure DevOps Pipelines 是更好的选择：

```yaml
# azure-pipelines.yml
trigger:
  branches:
    include:
      - master
  tags:
    include:
      - v*

pool:
  vmImage: 'windows-latest'

variables:
  solution: '**/*.sln'
  buildPlatform: 'Any CPU'
  buildConfiguration: 'Release'
  ssmsTestPath: 'D:\SSMS\TestEnvironment'  # 测试机 SSMS 路径

steps:
  - task: DotNetCoreCLI@2
    inputs:
      command: 'build'
      projects: '$(solution)'
      arguments: '--configuration $(buildConfiguration)'

  - task: DotNetCoreCLI@2
    inputs:
      command: 'test'
      projects: '**/*Tests.csproj'
      arguments: '--configuration $(buildConfiguration) --no-build'

  - task: CopyFiles@2
    displayName: '收集部署产物'
    inputs:
      SourceFolder: 'src/SSMS/bin/Release/net472'
      Contents: |
        SSMSBoostPlus.SSMS.dll
        SSMSBoostPlus.Core.dll
        *.pkgdef
        *.ctmenu
        DiffPlex.dll
        Serilog*.dll
        Microsoft.Data.SqlClient.dll
        Newtonsoft.Json.dll
      TargetFolder: '$(Build.ArtifactStagingDirectory)/Deploy'

  - task: PublishBuildArtifacts@1
    inputs:
      PathtoPublish: '$(Build.ArtifactStagingDirectory)/Deploy'
      ArtifactName: 'SSMSDeploy'
```

### 6.5 远程部署策略

CI 环境中通常没有 SSMS 22 安装，因此部署步骤需要区分对待：

**策略 A — 仅打包，人工部署**：Pipeline 只负责编译和产出 Artifact，由开发者下载后自行部署到本地 SSMS

**策略 B — SSH 推送到测试服务器**：通过 SSH 将产物推送到专用测试机的 SSMS 目录，适合有固定测试环境的团队

**策略 C — 自托管 Runner**：在安装了 SSMS 22 的机器上运行自托管 GitHub Actions Runner，可实现端到端的"编译+部署+冒烟测试"

### 6.6 优缺点

**优点**：
- 全自动化，代码提交即触发
- 版本与 Git Tag 绑定，可追溯任何版本的完整构建产物
- 多环境支持（dev/test/prod 分离）
- 内置测试门禁，防止带 Bug 的代码被部署
- 团队协作标准化

**缺点**：
- 初始搭建成本较高（Workflow 编写、Runner 配置、密钥管理）
- 对个人项目可能过重
- 远程部署需要额外的测试基础设施
- SSMS 22 是桌面应用，CI 环境难以做真正的集成测试（缺少 VS Shell 运行时）

### 6.7 适用场景

多人协作的正式项目、公开发布的开源项目、有固定测试服务器的企业团队、需要版本发布管理的成熟产品

## 七、方案组合推荐

上述五种方案并非互斥，可以根据不同阶段组合使用：

### 推荐组合 A：开发期（个人）

```
方案三（Post-Build 自动部署） + 方案四（PS 脚本作为补充）
```

日常开发靠 Post-Build 自动部署实现无缝迭代；遇到特殊情况（如全新环境初始化、排查部署问题）时用 PS 脚本的手动模式精细控制。

### 推荐组合 B：团队协作

```
方案三（开发期） + 方案二（VSIX 分发） + 方案五（CI/CD 发布）
```

- 开发者本地用 Post-Build 自动部署快速迭代
- 定期构建 VSIX 通过 CI/CD 发布到内部 Feed 或 GitHub Releases
-团队成员从统一位置安装稳定版本

### 推荐组合 C：正式发布

```
方案五（CI/CD 全流程） + 方案二（VSIX 打包） + 方案四（PS 脚本做现场部署）
```

- CI/CD 自动编译、测试、打 VSIX 包、创建 Release
- 用户通过 VSIX 安装器安装
- 特殊环境（无互联网隔离网段）用 PS 脚本手动部署
