## 一、改造动机

参考 `AIDoc/诊断报告/2026-07-02-deploy-to-ssms部署脚本问题诊断.md`，原 deploy-to-ssms.bat 存在 5 个 P0 致命问题：

| # | 问题 | 影响 |
|---|------|------|
| P0-1 | SSMS 22 路径硬编码 `D:\...` | 跨机器 100% 失败 |
| P0-2 | 项目路径硬编码 `F:\...` | 跨用户 100% 失败 |
| P0-3 | WebView2 NuGet 版本硬编码 1.0.2903.40 | 静默失败 |
| P0-4 | 未调用 `ssms.exe /setup` | 偶发扩展不加载 |
| P0-5 | 未检查 SSMS 进程 | 部署"假成功" |

### 改造目标

1. **路径 0 硬编码**：所有路径动态检测
2. **单一职责**：检测逻辑独立为 PS1 脚本
3. **完整健壮性**：进程检查、错误校验、强制刷新
4. **多端复用**：.bat / Agent / CI/CD 共用同一份检测代码

## 二、改造架构

```
┌──────────────────────────────────────────────────────────┐
│            diagnosis/Find-SSMS22Path.ps1                 │
│            (SSMS 22 路径检测唯一入口)                      │
│  - 6 Tier 检测策略                                        │
│  - 持久化到 %APPDATA%\SSMSBoostPlus\config.json         │
│  - 支持 -AsJson / -Source / -NoPersist 参数              │
│  - 退出码：0=成功，1=全部失败                             │
└──────────────────────────────────────────────────────────┘
              ↑                    ↑                    ↑
┌──────────────────┐  ┌────────────────────┐  ┌──────────────────┐
│ deploy-to-ssms   │  │ 小H Agent 文档     │  │ CI/CD 流水线     │
│ .bat             │  │ (步骤 3)            │  │ (未来扩展)        │
└──────────────────┘  └────────────────────┘  └──────────────────┘
```

### 6 Tier 检测流程

```
Tier 1: 用户配置 (config.json)
   ↓ 失败
Tier 2: 环境变量 (SSMS22_PATH)
   ↓ 失败
Tier 3: vswhere.exe
   ↓ 失败
Tier 4: 注册表 Uninstall
   ↓ 失败
Tier 5: 常见路径扫描 (D:/E:/F:)
   ↓ 失败
Tier 6: 运行进程探测
   ↓ 失败
返回 null，退出码 1
```

### .bat 调用 PS1 关键代码

```bat
for /f "usebackq delims=" %%P in (
    `powershell -NoProfile -ExecutionPolicy Bypass -File "%FIND_SCRIPT%" 2^>nul`
) do set SSMS_ROOT=%%P
```

## 四、关键技术点

### 4.1 PS1 脚本设计亮点

#### 模块化函数（6 Tier 独立）

| 函数 | Tier | 来源 |
|------|------|------|
| `Find-UserConfig` | 1 | `%APPDATA%\SSMSBoostPlus\config.json` |
| `Find-EnvVar` | 2 | `$env:SSMS22_PATH` / `$env:SSMS_INSTALL_PATH` |
| `Find-VSWhere` | 3 | `%ProgramFiles(x86)%\...\vswhere.exe` |
| `Find-Registry` | 4 | `HKLM\...\Uninstall` 节点 |
| `Find-CommonPath` | 5 | D:/E:/F: 盘扫描 |
| `Find-RunningProcess` | 6 | `Get-Process SSMS` |

#### 参数化控制

```powershell
[switch]$AsJson           # JSON 输出
[switch]$NoPersist        # 不写配置
[string]$Source = 'auto'  # 强制指定检测源
[switch]$VerboseOutput    # 详细日志
```

#### 路径验证

```powershell
function Test-SSMSRoot {
    param([string]$Path)
    $ssmsExe = Join-Path $Path 'Common7\IDE\SSMS.exe'
    return (Test-Path $ssmsExe)
}
```

#### 错误处理

- `try/catch` 包裹每个 Tier
- 进程探测支持多 SSMS 进程容错
- 注册表 `ErrorAction SilentlyContinue` 避免无权限错误

### 4.2 .bat 脚本设计亮点

#### 9 步完整流程

| Step | 内容 | 进度 |
|------|------|------|
| 0 | 管理员权限检查 | - |
| 0.5 | SSMS 22 进程检查（避免文件锁定） | - |
| 1 | 动态检测 SSMS 22 路径 | - |
| 2 | 验证编译产物（4 个核心 DLL） | - |
| 3 | 清理冲突目录 | - |
| 3.5 | 清空旧部署残留 | - |
| 4 | 复制核心 DLL（4 + 4 PDB） | 40% |
| 5 | 复制配置文件 | 60% |
| 6 | 复制第三方依赖 | 80% |
| 7 | 刷新配置标记 | 95% |
| 8 | 强制刷新 PkgDef 缓存 | - |
| 9 | 部署后验证 | 100% |

#### 自动推导项目目录

```bat
set PROJECT_DIR=%~dp0..
if "%PROJECT_DIR:~-1%"=="\" set PROJECT_DIR=%PROJECT_DIR:~0,-1%
```

#### WebView2 版本动态发现

```bat
for /d %%D in ("%USERPROFILE%\.nuget\packages\microsoft.web.webview2\*") do (
    set WEBVIEW2_NUGET=%%D
)
```

#### 强制 PkgDef 刷新

```bat
"%SSMS_EXE%" /setup
```

## 六、风险评估

### 6.1 改动风险

| 风险项 | 等级 | 缓解措施 |
|--------|------|---------|
| PowerShell 函数语法错误 | 低 | 6 Tier 互相独立 |
| Tier 3 vswhere 路径差异 | 低 | try/catch 包裹 |
| Tier 4 注册表读取权限 | 低 | `-ErrorAction SilentlyContinue` |
| Tier 6 进程 MainModule 失败 | 低 | 整体 try/catch |
| .bat 调用 PS1 启动稍慢 | 低 | 部署不是高频操作 |
| 跨平台不支持 | 无影响 | 项目本就是 Windows-only |
| 执行策略拦截 | 低 | `-ExecutionPolicy Bypass` |

### 6.2 兼容性

- 向后兼容：未修改任何外部 API
- 向前兼容：6 Tier 检测策略可应对未来路径变化
- 跨用户兼容：每个用户独立 `%APPDATA%` 配置文件

### 6.3 回滚方案

# 一键回滚
git checkout HEAD -- deploy-to-ssms.bat .codebuddy/agents/小H发布部署.md

## 七、关键决策记录

### 7.1 为什么选方案 4（不选 1/2/3）

| 方案 | 否决理由 |
|------|----------|
| 方案 1：仅输出报告 | 不能解决实际问题 |
| 方案 2：改 .bat 不抽脚本 | 路径检测逻辑与 .bat 耦合，难以复用 |
| 方案 3：完整重写 .bat | 改动量大，CI/CD 难以复用 |
| **方案 4：抽 PS1 + 改 .bat** | **单一职责，可测试，多端复用** ✅ |

### 7.2 为什么用 PS1 不用 Python/C#

- 项目本身是 .NET 生态
- .bat 调用 PowerShell 是 Win32 最佳实践
- PS1 在 Windows 上零依赖
- 未来 CI/CD Agent（Windows）直接复用

### 7.3 为什么 Tier 1 放最优先

- 用户配置是最快（零开销）的检测方式
- 检测成功后立即持久化，避免重复扫描
- 团队机器首次部署后，后续部署几乎零成本
