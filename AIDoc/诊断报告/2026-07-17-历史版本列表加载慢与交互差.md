## 问题现象

用户在「版本历史」工具窗口中选中一个对象（无论是搜索框选中、回车，还是 SSMS 活动窗口切换带动对象切换）后，下方 DataGrid 需要 10 秒以上才显示出该对象的历史版本列表。期间页面无任何进度指示，旧数据残留、新数据突然出现，用户无法取消、无法并行操作，只能被动等待。

## 加载链路还原（触发 → 取数 → 绑定）

触发入口有三条，最终都汇聚到 `LoadVersionsAsync`：

1. 搜索框选中对象：`ObjectSearchBox_SelectionChanged`（xaml.cs:510）→ `_ = LoadVersionsAsync(selected.ObjectName)`
2. 搜索框回车：`ObjectSearchBox_KeyDown`（xaml.cs:498）→ `_ = LoadVersionsAsync(text)`
3. SSMS 活动窗口切换：`OnWindowActivated → RefreshForActiveWindow`（xaml.cs:990-993）→ `await LoadVersionsAsync(objectName)`；若连接库也变了则走 `LoadForObject`（xaml.cs:944）整窗重载。

取数核心：`LoadVersionsAsync`（xaml.cs:445）→ `VersionHistoryService.GetObjectHistoryAsync`（VersionHistoryService.cs:26）。

## 根因分析

### RC1（高置信·确定性浪费）：列表查询 SELECT 了完整的 `sqlcommand` 大字段，但列表 UI 根本不展示它

`GetObjectHistoryAsync`（VersionHistoryService.cs:38-53）的 SELECT 列表包含 `sqlcommand` —— 即每行完整的历史脚本正文（存储过程 / 表 DDL，常达数十 KB 至数百 KB）。但 `VersionGrid` 的列绑定（LocalHistoryToolWindowControl.xaml:212-263）只用 `DatabaseName / RowNumber / FormattedTime / ChangeType / LoginName / Version`，**全程不展示 `sqlcommand`**。

`sqlcommand` 仅在两处被使用：
- 打开差异对比：`OpenDiffDialogAsync`（xaml.cs:688/697/699/729）读取 `record.SqlCommand`；
- 复制 SQL：`CopySql_Click`（xaml.cs:1103）读取 `record.SqlCommand`。

而这两处都可通过**已存在的** `GetVersionSqlAsync(connectionString, record.Id)`（VersionHistoryService.cs:218，按主键 `[ID]` 取单行，极快）在点击时按需补取。`MapRecord`（VersionHistoryService.cs:689）把 100 条脚本正文一次性读回并序列化，是本次卡顿最大、最确定的 I/O 浪费。

### RC2（高置信）：历史表缺少支撑索引，每次列表查询都是「全表扫描 + 排序」

查询形态（VersionHistoryService.cs:38-53）：
```sql
SELECT TOP(@top) ... FROM MESBASE.dbo.DBTrigger_Object_Version_Table
WHERE (objectname = @objectName OR objectname = @bareName) [AND databasename = @databaseName]
ORDER BY [PostTime] DESC, [ID] DESC
```
`DBTrigger_Object_Version_Table` 由 DDL 触发器在**所有库的所有对象**每次变更时写入，数据量可达百万级。过滤键是 `objectname`（+可选 `databasename`），排序键是 `PostTime, ID`。若表上缺少 `(objectname, [databasename], PostTime DESC, ID DESC)` 这类支撑索引，SQL Server 必须**扫描全表 → 应用 WHERE → 对匹配行排序 → 取 TOP 100**，在百万级表上稳定 10 秒级。

叠加 `OR [objectname] = @bareName`（VersionHistoryService.cs:51）会进一步破坏索引利用率（需两次定位/合并）。

> 建议补齐的覆盖索引（与 RC1 配合后，列表查询可做到「索引覆盖 + 不回表 + 不读大字段」）：
> ```sql
> CREATE NONCLUSTERED INDEX IX_ObjectVersion_ObjectName_Db_PostTime
>   ON dbo.DBTrigger_Object_Version_Table (objectname, databasename, PostTime DESC, ID DESC)
>   INCLUDE (eventtype, objecttype, loginname, hostname, Version);
> ```
> 注意 INCLUDE 中**不含 sqlcommand**——因为 RC1 已把它从列表查询剔除，使该索引成为覆盖索引，彻底避免 Key Lookup 与大字段读取。

### RC3（中）：重叠加载无取消、无合并，对象切换不防重入

- `ObjectSearchBox_SelectionChanged`（xaml.cs:510）与 `RefreshForActiveWindow`（xaml.cs:990）都以 `_ = LoadVersionsAsync(...)`（fire-and-forget）触发，且 `LoadVersionsAsync` 自身**没有 CancellationTokenSource**。用户快速切换对象 / 频繁切换 SSMS 窗口时，多个 `LoadVersionsAsync` 并发执行，各开一条连接、各跑一遍全表扫描，并竞争 `VersionGrid.ItemsSource`（最终显示的可能是较早触发的旧结果）。
- 对比：`DatabaseComboBox_SelectionChanged` 已用 `if (_isDatabaseComboBoxUpdating || _isLoading) return;`（xaml.cs:334）做防重入；但**对象选中路径没有同等保护**。

### RC4（中）：加载态交互差——无遮罩、无等待光标、不清理旧数据、不可取消

- `LoadVersionsAsync` 仅在状态栏写 `StatusText.Text = "加载中..."`（xaml.cs:451），`VersionGrid` 区**没有任何加载指示**（无 ProgressBar / 遮罩 / 转圈 / 变灰）。
- 加载开始时**不清空也不禁用** `VersionGrid`（xaml.cs:450-465）：旧对象的数据残留可见，10 秒后突然整批替换，用户无法判断「是否在加载 / 是否完成 / 显示的是不是当前选中对象」。
- 全程**未设置 `Mouse.OverrideCursor = Cursors.Wait`**，窗口看似「卡死」，加剧「只能干等」的观感。
- 无取消入口，用户只能被动等待。

### RC5（低-中）：`LoadForObject` 串行执行「对象列表查询 + 版本查询」，且每次新建连接用默认 15s 超时

- `LoadForObject`（xaml.cs:187-228）先 `await GetObjectListAsync`（GROUP BY 整表 + `OUTER APPLY (SELECT TOP 1 loginname ...)` 逐组子查询，xaml.cs:162-179），**再** `await LoadVersionsAsync`。首次打开 / 切库时两段重查询串行叠加，时间翻倍。
- `GetObjectHistoryAsync` 用 `new SqlConnection(...)` 每调用新建连接且**未设 ConnectTimeout**（VersionHistoryService.cs:59），走默认 15 秒；若 MESBASE 跨网络、连接池冷，open 自身即耗数秒，正好对应「10S+」量级。
- 无任何客户端缓存：同一对象短时内反复查看，仍每次全表扫描。

### RC6（低）：`async void` 入口无法 await / 取消 / 捕获

`LoadForObject`（xaml.cs:91）、`ObjectSearchBox_SelectionChanged`（xaml.cs:510）等为 `async void`，异常被静默吞掉、无法取消，从机制上堵死了「中断在途加载」的可能（与 RC3/RC4 互为因果）。

## 边缘情况与异常处理（修复时需覆盖）

- 懒加载 `GetVersionSqlAsync` 返回 null（记录被清理/并发删除）：差异弹窗应降级提示，不能崩溃（现有方法已返回 null，需在使用点判空）。
- 取消加载后再次选中同一对象：CTS 取消后 `_isLoading` 需正确复位（`finally` 中复位，注意异常与取消分支都要走 `finally`）。
- 索引 DDL 在超大表上创建会锁表/耗时，需在低峰执行并评估 `ONLINE` 选项（SQL Server Enterprise）。
- `async void` 改为可等待签名时，确保 SSMS 线程模型（JoinableTaskFactory）不被破坏。
